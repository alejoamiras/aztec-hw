# F — Modularity + Test-Coverage (holistic) — wave 2

Agent F (opus general-purpose). Scope: `ledger-app/src` + `ledger-app/tests` + `packages/adapter-ledger/src` (incl `*.test.ts`) + `packages/core/src`. NOT frontend. Dedup'd against AHW-001..094 (read full index). All line numbers + test (non-)existence verified by reading the files / grepping the test dirs.

The headline gap: the index already covers a LOT of structural test gaps (AHW-024/025/026/046/074/090/091) and monoliths (AHW-009/070). What survives novel is **the on-device strict-allowlist reject arms in `append_call.c` — the actual clear-signing security boundary — have no targeted negative test**, and **the device's own low-S/dual-sig anti-malleability + fault-detection arms are asserted by no automated test** (the "Confirmed-clean: malleability enforced" negative rests on a code read, not a test). Plus a cluster of duplicated C security primitives distinct from the canonical-path/hash dups already filed.

### F-F-1: APPEND_CALL strict-allowlist reject arms (0x6F09/0x6F0A/0x6F0B/0x6F0C) have NO targeted negative test — the fuzzer only checks "SW ∈ known-set", which a degraded gate would still pass
- Severity: MED — these four arms ARE the on-device clear-signing trust boundary (the whole point of "clear-sign, don't blind-sign"). A regression silently turning the `from==consumer` delegated-spend gate (or the visibility/arg-count/verb gates) into an accept would be caught by NOTHING in the suite. Real security consequence, hence MED not LOW.
- Owned: OURS
- Category: TEST
- Location: `ledger-app/src/handler/append_call.c:114,133,135,139,144` (the reject sites: `SW_DECODER_DESYNC` 0x6F0A, `SW_DECODER_MISS` 0x6F09, `SW_VISIBILITY_MISMATCH` 0x6F0B, `SW_DELEGATED_SPEND_UNSUPPORTED` 0x6F0C). Test that SHOULD exist: a Speculos negative file (sibling to `wire-negative.test.ts`, which today only exercises BEGIN_AUTHWIT/BEGIN_DEPLOY arms) OR added cases in `packages/adapter-ledger/src/verified-calls-content.test.ts`.
- What: I grepped every `*.test.ts` + `ledger-app/tests/*.py` for `0x6f09/0a/0b/0c`. The ONLY references are: (a) `apdu.ts` (the host mirror constant), and (b) `ledger-app/tests/wire_host/fuzz_append_call.c`. The fuzzer's check is `is_known_append_sw(sw)` — it `__builtin_trap()`s only if the SW is OUTSIDE the known set (`fuzz_append_call.c:31-46`). It accepts `0x9000` for ANY input. So if `verb_is_4arg_transfer` started returning false (delegated-spend gate disabled → device signs a transfer where `from != you`), the fuzzer would see `0x9000`, deem it "known", and pass. `wire-negative.test.ts` never sends APPEND_CALL. `verified-calls-content.test.ts` exercises exactly ONE append reject arm (DRIP non-TOKEN args[0] → 0x6F08, AHW-041) and otherwise only the ACCEPT path. The delegated-spend gate — explicitly called out in the file header as "removes the delegated-spend surface the PoC UI cannot honestly explain" — is asserted by zero tests.
- Attack/impact: maintainability + latent security — a future refactor of `handler_append_call` that weakens any of the four gates ships green. Specifically: SW_DELEGATED_SPEND_UNSUPPORTED is the gate that stops a host getting the device to clear-sign a transfer spending someone else's balance; SW_VISIBILITY_MISMATCH stops a public/private flag flip vs the verb.
- Evidence: `fuzz_append_call.c:31-46` (known-set membership, not input→SW mapping); `wire-negative.test.ts:40-72` (BEGIN_* only); `verified-calls-content.test.ts:216-244` (only 0x6F08). append_call.c:142-146 is the self-spend gate.
- Fix sketch: add 4 Speculos cases that BEGIN_AUTHWIT(count=1, consumer=X) then APPEND_CALL a body crafted to hit each arm, asserting the exact SW: a 4-arg transfer with `args[0]!=consumer` → 0x6F0C; a public-flag call against a private verb → 0x6F0B; wrong arg_count → 0x6F0A; an unknown selector on a registry-hit target → 0x6F09. (These need no reveal — all reject pre-FINALIZE/pre-UI, like the existing 0x6F08 case.)
- Confidence: high
- Dedup-check: distinct from AHW-024 (malformed-frame-mid-stream / wrong-STATE 0x6F11), AHW-025 (glitch-sim of the args_hash *fault* arms), AHW-046 (review-CONTENT on the accept path), AHW-091 (the binding/finalize tail structurally outside the fuzz oracle). NONE of those assert these four allowlist arms fire on a crafted input. Novel.

### F-F-2: Device-side anti-malleability (low-S) + fault-detection (dual-sig dup) reject arms are asserted by NO automated test; the index's "malleability enforced" negative rests on a code read
- Severity: MED — signature malleability is a named protocol risk (CLAUDE.md adversarial checklist) and the index records "ECDSA-K low-`s` enforced" as a Confirmed-clean negative — but that negative is backed only by reading the C, not by any test. `SW_DUP_SIG_MISMATCH` (0x6F06), the fault-injection backstop on the duplicate ECDSA sign, is asserted nowhere. A silent regression (e.g. dropping the `if (s_is_high(s)) low_s_normalize(s);` call) ships green and the device starts emitting malleable high-S sigs.
- Owned: OURS
- Category: TEST
- Location: device impls `ledger-app/src/handler/sign_outer_hash.c`, `finalize_and_sign.c`, `finalize_deploy_and_sign.c:59-81,295,315,317` (`s_is_high`/`low_s_normalize`/dup-sig compare → 0x6F06). A device-output assertion belongs in `ledger-app/tests/test_sign_outer_hash.py` (extend `test_sign_outer_hash_happy_path` to parse `r||s` and assert `s <= SECP256K1_HALF_N`), and/or a Speculos sign test that verifies the returned sig with `@noble/curves` (see F-F-3).
- What: There IS a host low-S test — `packages/core/src/ecdsa.test.ts:43-52` (`normalizeLowS`). But that exercises the **host `core` `normalizeLowS`**, a SEPARATE implementation from the device's three duplicated C `low_s_normalize` bodies. No test asserts the DEVICE actually returns low-S, and no parity test binds the host `core` low-S to the device's. `test_sign_outer_hash.py:80` (happy path) captures `r||s` but never inspects `s`'s magnitude. Grep for `6f06`/`DUP_SIG` across all test dirs = zero hits (confirmed).
- Attack/impact: a third party who observes a device ECDSA sig could flip `s → N-s` to mint a second valid signature over the same message (classic malleability) if the device stopped normalizing — undetected by CI. The dup-sig fault arm (0x6F06) is the device's defense against a glitched single ECDSA sign; untested, a regression that signs once (no cross-check) is invisible.
- Evidence: `finalize_and_sign.c`/`finalize_deploy_and_sign.c:295,315` low-S + `:317,323` dup compare → `SW_DUP_SIG_MISMATCH`; `core/src/ecdsa.test.ts` tests host only; `test_sign_outer_hash.py` happy path doesn't assert `s` range; index Confirmed-clean "ECDSA-K low-`s` enforced (codex)" is a read, not a test.
- Fix sketch: in `test_sign_outer_hash.py`, after the happy-path sign, assert `int.from_bytes(s) <= SECP256K1_HALF_N`. Best: add a Speculos sign test that `secp256k1.verify`s the returned `r||s` against the device pubkey AND asserts low-S (this doubles as the F-F-3 / AHW-087 host-verify gap). 0x6F06 needs a glitch-sim (folds into AHW-025's framing but is a concrete distinct uncovered arm).
- Confidence: high
- Dedup-check: AHW-025 is "fault-injection reject arms have no glitch-sim test" — that's the right bucket for the 0x6F06 *glitch* path, but it does NOT cover low-S (which is not a fault arm — it's an always-on malleability normalization with zero test) nor does it note that the malleability Confirmed-clean negative is test-less. The low-S half is novel; the 0x6F06 half overlaps AHW-025 and I flag it as an enrichment of AHW-025 if you prefer to fold.

### F-F-3: `verified_calls_ui.c` `render_call_pairs` is a 95-line per-verb switch that the security boundary (display==signed) depends on, untestable off-device
- Severity: LOW — real modularity smell with a security shadow (AHW-040/086 both lived here, in this exact switch), but it IS now content-tested end-to-end on the accept path (AHW-046 / `verified-calls-content.test.ts`), so the consequence is bounded.
- Owned: OURS
- Category: MODULARITY
- Location: `ledger-app/src/ui/verified_calls_ui.c:232-325` (`render_call_pairs`, the per-verb pair-emitting switch); the file is 385 LOC (the named candidate).
- What: `render_call_pairs` hard-codes, per verb arm, which args map to From/To/Amount/Flags/Via pairs by index (`c->args[0]`, `c->args[1]`, `c->args[2]`) inline with NBGL pool-index bookkeeping (`g_pairs[out_idx + pairs_added]`). The arg→label mapping (the actual "what the user sees vs what's signed" contract) is entangled with the NBGL static-pool plumbing, so it can only be verified by booting Speculos and scraping screen text — there is no pure unit that maps `(verb, args[]) → (label,value)[]` testable on the host. Every render-vs-sign bug found so far (AHW-040 DRIP, AHW-086 flags-only-in-transfer, AHW-050 truncation) traces to a missing/asymmetric arm in this one function.
- Attack/impact: maintainability — a contributor adding a verb (or reordering an arg) must re-derive the pool bookkeeping by hand; the only safety net is the heavyweight Speculos content test. A pure arg→pairs projection would be unit-testable per verb in milliseconds and would have caught AHW-040/086 at compile-adjacent speed.
- Evidence: `verified_calls_ui.c:232-325`; the bugs AHW-040/050/055/086 all cite this function.
- Fix sketch: extract a pure `cs_project_call_pairs(const l4_call_t*, const cs_registry_entry_t*, const cs_verb_entry_t*, out_pairs[], &n)` that takes/returns plain structs (no NBGL globals); host-compile it (like the `wire_host` / `poseidon2_host` harnesses) and table-test every verb's arg→label mapping. The NBGL caller just copies the projected pairs into the static pool.
- Confidence: high
- Dedup-check: AHW-009 is the `aztec-ledger-session.ts` (TS) monolith; AHW-046 added the *content test* but did NOT make the renderer unit-testable (it tests through Speculos). This is the structural "the renderer can't be unit-tested in isolation" finding for the C UI. Novel.

### F-F-4: `ct_memcmp32` — a constant-time-ish equality primitive on security-critical values — is copy-pasted into 5 handler files; `low_s_normalize`/`s_is_high`/`SECP256K1_HALF_N` triplicated into 3
- Severity: LOW — duplication that can drift independently; each `ct_memcmp32` copy gates a real security decision (address/pkh/outer_hash/args_hash equality). If one copy is "optimized" to an early-return `memcmp`, that handler's gate silently becomes timing-variable / short-circuiting while the others stay hardened — exactly the AHW-070/008 drift-risk class, but for different primitives.
- Owned: OURS
- Category: MODULARITY
- Location: `ct_memcmp32` defined identically in `append_call.c:65`, `begin_deploy_account.c:51`, `finalize_deploy_and_sign.c:53`, `finalize_and_sign.c` (grep-confirmed 5 files incl `get_aztec_master_secret.c`). `low_s_normalize`+`s_is_high`+`SECP256K1_HALF_N[32]` defined identically in `sign_outer_hash.c`, `finalize_and_sign.c`, `finalize_deploy_and_sign.c:41-81`.
- What: Five byte-identical `ct_memcmp32` bodies and three byte-identical low-S normalizers. The low-S triplication is the more dangerous: it's the malleability defense (F-F-2), and the half-order constant `SECP256K1_HALF_N` is hand-hardcoded in each — a typo in one copy is a per-handler malleability hole with no shared test (F-F-2) to catch it.
- Attack/impact: maintainability + latent security; a fix/hardening applied to one copy (or a bug introduced in one) doesn't propagate. The `reject(uint16_t)` helper is also 5×-duplicated but that one is benign boilerplate (just `l4_session_reset()` + `io_send_sw`).
- Evidence: grep `static int ct_memcmp32` → 5 files; `static void low_s_normalize` → 3 files; `SECP256K1_HALF_N`/`_DEPLOY` hardcoded per sign handler.
- Fix sketch: move `ct_memcmp32` to a shared `l4/ct.h` (or reuse the existing `crypto_helpers`), and the low-S normalize + half-order constant into a single `crypto/ecdsa_lows.{c,h}` consumed by all three sign handlers. Pairs naturally with F-F-2 (one shared low-S impl → one shared test).
- Confidence: high
- Dedup-check: AHW-070 (canonical-path inline copies) and AHW-008 (canonical-hash TS block) are SPECIFIC to those two primitives. Neither covers `ct_memcmp32` (a different security primitive) nor the low-S triplication. Novel.

### F-F-5: `wire-negative.test.ts` reads its OWN ad-hoc SW table instead of importing the shared `apdu.ts` SW enum — drift between the device-fact constants and the test's expectation is invisible
- Severity: LOW — a test-correctness/maintainability gap: the negative-test oracle could silently assert against a stale status-word number.
- Owned: OURS
- Category: TEST
- Location: `packages/adapter-ledger/src/wire-negative.test.ts:18-26` (local `const SW = { HASH_MISMATCH: 0x6f01, BAD_VERSION: 0x6f02, … }`), duplicating the canonical `SW` exported from `apdu.ts` (which mirrors `sw.h`). Same pattern in `wire-differential-replay.test.ts:52-53` (`SW_OK`/`SW_DEPLOY_PUBKEY_HASH_MISMATCH` redefined as locals).
- What: Two device-fact constants (the firmware status words) are re-typed by hand inside test files rather than imported from the single host mirror `apdu.ts`. If `sw.h` renumbers an SW and `apdu.ts` is updated but these local tables aren't, the negative test keeps asserting the OLD number — it'd pass against a device that no longer returns it (or fail spuriously), and the "fail-closed with the RIGHT SW" guarantee silently rots.
- Attack/impact: maintainability — a status-word renumber (plausible pre-audit, e.g. removing the dead 0x6F07/0x6F10 per AHW-058) desyncs the test oracle from device reality with green CI.
- Evidence: `wire-negative.test.ts:19-26` local SW map vs `apdu.ts` `SW` enum; `wire-differential-replay.test.ts:52-53` locals.
- Fix sketch: import `SW` from `apdu.ts` in both files; delete the local tables. (And, per the schema/contract-drift theme, consider a test asserting `apdu.ts` `SW` === the values parsed from `sw.h` so the host mirror itself can't drift — adjacent to AHW-058's dead-SW concern.)
- Confidence: high
- Dedup-check: distinct from AHW-058 (dead SW constants 0x6F07/0x6F10) and AHW-011 (untyped Speculos JSON casts). This is "the negative-test oracle hand-copies device constants." Novel.

### F-F-6: No test asserts the `kind==='deploy'` ⇔ `ledgerDeployContext`-present invariant, AND the existing entrypoint test only covers the policy guards — the actual device-flow branch selection in `wrapExecutionPayload` is untested off-device
- Severity: LOW — defense-in-depth/observability; the device fail-closes either way (so not exploitable), but the host-side mode-select is an unauthenticated sideband with no unit test pinning it.
- Owned: OURS
- Category: TEST
- Location: `packages/adapter-ledger/src/clear-signing-entrypoint.ts:127-135` (the `if (deployContext) {…} else {…}` branch). Test should live in `clear-signing-entrypoint.test.ts` (which today, lines 44-141, tests ONLY `#assertClearSignPolicy` throw-arms + the AHW-057 abort-on-throw).
- What: `clear-signing-entrypoint.test.ts` is good for what it covers (the 6 policy reject-arms + abort-on-throw), but it never asserts the branch CONTRACT: that `wrapExecutionPayload` WITH a context runs `#deploySignOnDevice` (not the tx path) and WITHOUT one runs `#clearSignOnDevice`. A future edit flipping the branch condition (or AHW-093's missing kind-vs-context assert) would compile and pass every existing test — the deploy could silently downgrade to a verb review. `createTxExecutionRequest` is also never tested for "a stray deployContext on a tx is ignored/rejected."
- Attack/impact: maintainability — the most security-sensitive seam's mode selection (deploy-sovereignty review vs verb review) has no unit pin; only the on-chain e2e exercises which branch fires.
- Evidence: `clear-signing-entrypoint.ts:127`; `clear-signing-entrypoint.test.ts` covers guards + abort only (no branch-selection assert).
- Fix sketch: add two tests with a spy `LedgerProvider` (record which device methods are called): `wrapExecutionPayload` + valid ctx → asserts `beginDeployAccount`/`finalizeDeployAndSign` called; `wrapExecutionPayload` no ctx → asserts `beginAuthwit`/`appendCall`/`finalizeAndSign` called. Pin AHW-093's invariant in the same file.
- Confidence: high
- Dedup-check: AHW-093 is the missing runtime ASSERT (code fix); AHW-090 tests the salt/profileId threading. This is the missing TEST that the branch SELECTION is correct — a different uncovered behavior. Adjacent to AHW-093 but distinct (test vs code); fold into AHW-093 if you prefer one entry.

## Strengths (well-modularized / well-tested — auditor-facing balance)

- **Deploy outer-hash recompute is exemplary.** `az_deploy_compute_outer_hash` (the device's deploy-authwit hash) is byte-exact differential-tested against the genuine `@aztec` entrypoint over 16 random `(account, fpc, nonce, chain, version)` vectors (`deploy-outer-hash-parity.test.ts:104-127`, `provider.m8.test.ts`), with the sponsor selector pinned (0x23d77f89). This is the gold standard the other paths should match.
- **The crypto primitives have real host-compiled parity harnesses**, not just happy-path: `poseidon2_host`, `grumpkin_host` (incl. a `dudect` timing harness + `grumpkin-point-add-edge.test.ts`), `blake2s_host`, plus TS parity suites (`schnorr-parity`, `pedersen-parity`, `grumpkin-*-parity`, `l4-manifest-parity`). The EC/field layer is densely covered.
- **The host `LedgerProvider` length parsers are uniformly exact-equality + fail-closed** (`provider.ts` — every `r.data.length !== N` throws), and `encodePath` rejects empty/overlong/non-uint32 components (`:243-263`). Python suite confirms the device mirror (`test_get_public_key.py` rejects empty/overlong/trailing/display-mode paths).
- **`#assertClearSignPolicy` IS unit-tested** for all six fail-closed arms + the AHW-057 abort-on-throw (`clear-signing-entrypoint.test.ts`) — the central host seam's guards are not the gap (the device-flow branch selection is, F-F-6).
- **`session-embedded-wallet.ts` is a model of avoiding boundary `as`-casts**: it subclasses `EmbeddedWallet` with type-safe getters specifically to NOT do `as unknown as { pxe }` (documented at `:8-12`), and the host-side cross-module types (`AzManifestHeader`/`AzCall`/`DeployContext`) are properly `interface`-typed in `apdu.ts`/`deploy-context.ts` — the only `as unknown as` in non-test src is the one it explicitly calls out as a lie it refuses to ship. Boundary typing on the TS side is strong.
- **The deploy handlers' 3-pass fault-recompute discipline is consistent** across BEGIN (2 passes) + FINALIZE (3rd pass) with explicit-bzero on every error path; the `claimed_outer_hash_received` bool correctly avoids the "Fr(0) is valid" pitfall (`finalize_deploy_and_sign.c:119`).
