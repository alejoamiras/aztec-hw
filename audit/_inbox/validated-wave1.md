## 2. Ready-to-index blocks (ACCEPTED, AHW-084..094, severity order)

### AHW-084 · MED · WIRE · OURS · VALIDATED
**Domain-separator constants hardcoded in the host wire with no equality guard.** `l4-manifest.ts:37-40` hardcodes the four Aztec poseidon2 separators as literals (`SIGNATURE_PAYLOAD=463525807`, `PUBLIC_CALLDATA=2760353947`, `FUNCTION_ARGS=3576554347`, plus the dead `_AUTHWIT_OUTER=3283595782`) under a comment "must equal the device-side constants in `l4/wire.h`" (`:36`). They are consumed on the live signing wire at `:58` (`paddingArgsHash`) and `:72`/`:77` (`encodeRealCall` argsHash). VERIFIED the literals match `@aztec/constants@4.2.1` exactly today (no live mismatch), and `wire.h:78-80` matches too — but there is NO `===` assertion binding the literals to `DomainSeparator` from `@aztec/constants`, unlike upstream `@aztec/entrypoints/encoding.ts` which imports the enum. On an `@aztec/*` bump that renumbers a separator, `encodeRealCall`'s streamed `argsHash` silently desyncs from canonical → every clear-sign fails closed with `SW_HASH_MISMATCH` (availability), OR the `l4-manifest-parity.test.ts` catches it first. Fail-closed, not attacker-triggered, but a hardcoded crypto constant in the signing path with no drift guard is a latent correctness hole. The `_AUTHWIT_OUTER` literal is already dead (prefixed `_`, never used). **Sev MED (borderline, kept):** load-bearing for the args_hash the device consumes; fail-closed mitigates impact. **Fix dir:** import `DomainSeparator` from `@aztec/constants`, or add a test asserting each literal `===` the matching member; drop the dead `_AUTHWIT_OUTER`. **Dedup:** distinct from AHW-035 (codegen artifact provenance) + AHW-015 (the `deviceOuterHashForIntent` parity-anchor comment) — this is the live-wire separator literals, neither codegen nor comment. **Src:** F-C-2.

### AHW-085 · MED · FW-STATEMACHINE · OURS · VALIDATED
**Authwit FINALIZE re-hashes the cached `args_hash`, never re-derives it from stored raw args.** `session.h:40-46` documents that raw args are stored for "M5.2's three-pass finalize re-derivation from stored raw args," but the three finalize passes (`finalize_and_sign.c:165-219`, all calling `l4_compute_outer_hash`) consume the cached `call->args_hash` via `parity.c:57-58` (`emit_call_fields` `memcpy(... call->args_hash ...)`); `l4_compute_outer_hash` (`parity.c:85-137`) never recomputes per-call `args_hash` from `call->args[]`. The cached value is written once at APPEND_CALL with a double-recompute + cross-check + canonical check (`append_call.c:160-181`). So a fault/glitch (or latent corruption) that tampers `slot->args_hash` (or `slot->args[]`) BETWEEN `APPEND_CALL` and `FINALIZE_AND_SIGN` is NOT caught by the advertised three-pass re-derivation — all three passes re-hash the same corrupted cached field and agree. The outer-hash 3-pass + B3 consumer-binding still hold, so this is a narrow defense-in-depth / comment-truth gap on the hardening, not a demonstrated host exploit. **Sev DOWNGRADE-then-ACCEPT at MED (candidate said MED):** fault injection is in a HW-wallet threat model, but exploitation needs a precise post-APPEND glitch on cached session state and the consumer binding is independent — this sits at the MED/LOW boundary; kept MED because the code actively claims a hardening it does not perform (dangerous-direction comment + real gap). **Fix dir:** in `l4_compute_outer_hash`, recompute each call's `args_hash` from `selector + args[] + is_public` every pass and compare against the cached value before use. **Dedup:** distinct from AHW-025 (missing GLITCH-SIM TESTS) — this is an implementation/comment-truth gap in the hardening itself, not a test gap. **Src:** F-A-1.

### AHW-086 · MED · FW-UI · OURS · VALIDATED
**Call flags STATIC / HIDE_MSG_SENDER are signed but NOT rendered for MINT / DRIP / SPONSOR verbs.** `parity.c:62-67` (`emit_call_fields`) binds `is_public`, `hide_msg_sender`, `is_static` as Fr fields into the inner_hash → outer_hash for EVERY call. `append_call.c:110-146` validates only `flags & ~L4_CALL_FLAG_MASK` (`:111`) and `is_public` vs the verb (`:137-139`) — STATIC/HIDE_MSG_SENDER are left unconstrained for ALL verbs. `verified_calls_ui.c`: `format_mode` (the only code surfacing STATIC/HIDE_SENDER, `:139-159`) is called ONLY in the TRANSFER arm (`:261`). The MINT arm (`:276-293`), SPONSOR arm (`:294-301`), and DRIP arm (`:302-320`) emit NO Flags pair. So a patched host can stream a MINT/DRIP/SPONSOR call with `HIDE_MSG_SENDER` (or STATIC); the device binds the flag into the approved signature but shows no indication. Blast radius bounded: `is_static=true` makes a state-changing mint/drip revert on-chain (self-defeating), and the flag is still cryptographically bound (no forgery) — so this is a transparency/clear-signing-completeness break, not theft, but it violates "what is rendered == what is signed" for 3 of 4 verb families. **Sev MED (kept):** same render-vs-sign class as AHW-040, narrower blast radius. **Fix dir:** emit the Flags pair for any verb when `c->flags & (STATIC|HIDE_MSG_SENDER)`, OR reject non-zero STATIC/HIDE_SENDER on verbs whose UI doesn't display them in `append_call`. **Dedup:** distinct from AHW-040 (DRIP value pairs, fixed) + AHW-055 (mint warning salience). NB this DIRECTLY refines the index "Confirmed-clean" note (line 437) "Clear-sign flags … bound into the inner_hash — no display-vs-sign gap": that negative verified BINDING but never verified DISPLAY per-verb. **Src:** F-B-1.

### AHW-087 · LOW · WIRE · OURS · VALIDATED
**Live Ledger adapter never verifies the device's returned signature against the account pubkey.** `provider.ts:151-167` (`finalizeAndSign`) / `:196-212` (`finalizeDeployAndSign`) length-check `r||s` (64 B) and return it; `clear-signing-entrypoint.ts:176`/`:231` wrap it straight into `new AuthWitness(messageHash, packEcdsaSignature(r,s))` with zero verification. The host caches the account pubkey (`auth-witness-provider.ts:79-89` `getPublicKeyXY`) and bundles `@noble/curves`, but never `secp.verify(r‖s, sha256(outerHash), pubkey)`. A MITM/compromised `LedgerTransport` returning any well-formed 64-byte blob with `sw=0x9000` is trusted; the bad sig only fails late in-circuit (opaque error) instead of an immediate local reject. No fund loss — Aztec's in-circuit verifier is the backstop — pure defense-in-depth + clearer-error miss. **Fix dir:** after finalize, `secp256k1.verify(r‖s, sha256(outerHashBytes), cachedPubkey)` (+ Grumpkin-Schnorr equivalent); throw on failure. **Dedup:** AHW-075 is the SAME principle but was scoped to the DELETED `adapter-trezor` package (DISSOLVED per index line 62 + its "delete with the package" note). ### AHW-089 · LOW · WIRE · MIXED · VALIDATED
**Auto-authwit fail-close (AHW-001) is silently swallowed upstream — no user signal.** `EmbeddedWallet.sendTx` derives app-authwits from offchain effects in `embedded_wallet.js:85-98`: `offchainEffects.map(async … try{ this.createAuthWit(...) }catch{ return undefined })`, then pushes only truthy witnesses. The user never sees "this flow needs an authorization the device can't clear-sign yet." ### AHW-092 · LOW · MODULARITY · OURS · VALIDATED
**Shared binding helper defaults unknown constructor schemas to ECDSA; FINALIZE never re-checks the schema.** `account_binding.c:57-72` (`account_binding_deploy_partial`) handles `CS_DEPLOY_ARG_SCHEMA_SCHNORR_PUBKEY_XY` explicitly (`:64`) and sends EVERY other `arg_schema` down the ECDSA `az_deploy_compute_partial_address` path (`:69`). ### AHW-093 · LOW · WIRE · OURS · VALIDATED

This is the missing MODE-CONSISTENCY assert — a distinct sub-point, but note its sibling AHW-005 is already PARKED, so this is a thin defense-in-depth add. **Src:** F-C-1.
