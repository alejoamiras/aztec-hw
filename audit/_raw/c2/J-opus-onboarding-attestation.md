# Pass J (opus) — Onboarding + attestation + sovereignty trust-chain red-team

Scope: the device↔host address-binding / attestation surface — `onboarding.ts`,
`master-secret.ts`, `provider.ts`, `session-embedded-wallet.ts`, `auth-witness-provider.ts`,
`account-contract.ts`, `ledger-account-contract-base.ts`, `aztec-ledger-session.ts` (connect),
+ device `get_aztec_master_secret.c` / `get_public_key.c` / `get_schnorr_pubkey.c`, and the
address-pill trust path through `OnboardPanel.tsx` / `AccountPanel.tsx` / `TransferPanel.tsx`.

The question: how does the host establish that an Aztec address is genuinely controlled by THIS
device, and can a malicious host / MITM transport make the user trust a host-chosen address, a
replayed attestation, or a spoofed "verified on device" state?

Read every file end-to-end + the device handlers + the deploy/B3 binding. Verified line numbers
by reading. Dedup'd against AHW-001..094 (`index.md`) + the in-flight `_state.md` wave-1/wave-2
inbox (A/B/C/D/E/F). Candidate IDs F-J-N.

**Headline:** the transfer/drip (B3) and DEPLOY paths ARE genuinely device-attested (the
prior campaign's confirmed-clean holds — verified independently below). But there is a NEW,
distinct gap on the **onboarding / receive-identity** surface: the account address the user sees
and acts on at onboard is **100% host-derived and never attested by the device at onboard**; the
device's only onboard cross-check (the reveal "Confirm" checksum) binds the *secret*, NOT the
address. For an already-deployed account the device address-attestation step (deploy review) is
SKIPPED entirely, so it can never fire. A malicious host can therefore present a host-chosen
address as the user's "device account" with a green, genuinely-matching device checksum.

### F-J-1: The onboard account address is host-derived and NEVER device-attested; the only device cross-check (reveal checksum) binds the SECRET, not the address — a malicious host can present a host-chosen address as the user's device account
- Severity: **HIGH** — defeats the core "this address is controlled by your device" guarantee on the receive/identity surface; a malicious host shows a host-chosen address as device-backed with a genuinely-matching on-device checksum, and (for an already-deployed account) no device path ever attests the real address.
- Owned: OURS
- Category: DESIGN
- Location: `aztec-ledger-session.ts:252-256` (host derives `accountManager.address` from `secret`+`salt`+pubkey, no device address round-trip), `onboarding.ts:42-57` (`revealMasterSecret` returns `{secret, checksum}` — checksum is over the SECRET), `master-secret.ts:79-85` (`masterSecretChecksum` = `SHA-256("aztec-vk-confirm-v1" ‖ secret)[0..1]`, **16 bits**, secret-only), `master_secret_reveal_ui.c:64-86` (device shows `Account #N` + `Confirm` checksum — **no address**), `OnboardPanel.tsx:103` (`addressHex = session.address.toString()`), `OnboardPanel.tsx:199-204` ("Device checksum … should match the device screen"), `AccountPanel.tsx:93` (renders `session.addressHex` as the account address), `TransferPanel.tsx:163-172` ("Use my address" → `sessionRef.addressHex` as a send/receive target). Device side confirmed: `get_aztec_master_secret.c` + `get_public_key.c` NEVER read or render any address (grep-empty); the only handler that takes `expected_address` and re-derives+rejects is the DEPLOY path (`begin_deploy_account.c:150-153`, `finalize_deploy_and_sign.c:174-183`).
- What: At onboard the host (a) reveals the device master secret (one approval, device shows a 16-bit checksum of the SECRET), (b) fetches the signing pubkey approval-free, then (c) **computes the Aztec address entirely host-side** via `AccountManager.create(secret, contract, salt)` (address = f(deriveKeys(secret), classId, ctor-args=pubkey, salt) — no device call; the file's own comment at `:219` says "AccountManager.create(...) derives the address … "). The device at onboard attests the *secret* (via the checksum the user is told to compare) but **never the address**. The address only becomes device-attested if and when the user runs a Deploy (device re-derives pkh+address from its own secret, `address_local`, and shows 8+6 on the deploy-review screen) or a Transfer/Drip (B3 `b3_verify_consumer_is_this_account`). The UI shows the host-derived address pill and a "✓ on-chain" badge BEFORE either of those, and `AccountPanel.tsx:28-29` SKIPS Deploy entirely when `alreadyDeployed` (set from `session.isDeployed()`, a host-controlled node query) — so for the common "reconnect an existing account" flow the device address-attestation **never runs**.
- Attack/impact: A malicious host (compromised dApp bundle / supply-chained `apps/*` / hostile `AztecLedgerSession` consumer) does a genuine reveal so the on-device "Confirm" checksum matches what the host prints (the checksum is over the secret, which the host legitimately received — so it ALWAYS matches regardless of what address the host then shows). The host then displays an attacker-chosen address in the pill (fabricated string, or a real address derived with a different salt/account that the attacker controls) and forces `alreadyDeployed=true` (it controls the node response feeding `isDeployed()`) to suppress the only device address-attestation step. The user, having been told "Device checksum `abcd` — should match the device screen" and seeing it match, reasonably believes the displayed address is device-verified, and copies it to receive funds (or treats it as their on-chain identity). **The displayed receive address is host-chosen with a green device cross-check.** Funds sent there go to the attacker; the user has no on-device surface that ever showed the real address. This is the literal "host presents a host-chosen address as device-verified" scenario — for the receive/identity path, which (unlike send) never reaches the device.
- Evidence: the onboard device handlers touch no address (grep over `get_aztec_master_secret.c`/`get_public_key.c` for "address" returns empty); `master_secret_reveal_ui.c:80-86` review pairs are `Account #N` + `Confirm` checksum only; `masterSecretChecksum` (`master-secret.ts:84`) is `…subarray(0, 2)…` = 2 bytes = 16 bits, computed from the SECRET; `OnboardPanel.tsx:199-204` tells the user the checksum "should match the device screen" (true — but it certifies the secret, not the address the same panel feeds into the pill); `AccountPanel.tsx:93` + `TransferPanel.tsx:167` consume `addressHex` as the user-facing account/receive address; `AccountPanel.tsx:28,110` gates out Deploy on `alreadyDeployed`. The deploy review (`deploy_review_ui.c:104-105`) explicitly shows the DEVICE-derived `address_local` "NOT the host-claimed expected_address" — proving the team KNOWS the address must be device-authored to be trusted, but that discipline exists ONLY on the deploy path, not at onboard/receive.
- Fix sketch: the device must attest the address (or a strong fingerprint of it) on a surface the user sees at onboard — e.g. an approval-gated `GET_AZTEC_ADDRESS` INS that the device derives from its own secret+salt+pubkey (same math as the deploy path's `address_local`) and renders 8+6, so the host cannot substitute it; OR fold the address fingerprint into the reveal "Confirm" pair (show `addr_8_6` alongside, not just a secret checksum); OR, minimally, never render an account address as device-associated until a device path (deploy/B3) has attested it, and stop auto-suppressing Deploy on a host-supplied `alreadyDeployed`. Also widen the secret checksum beyond 16 bits if it's kept as a user-facing integrity anchor.
- Confidence: high
- Dedup-check: distinct from **AHW-047** (reveal exports the privacy ROOT — that's about the SCOPE of what reveal discloses; this is about the ADDRESS not being device-attested). Distinct from **AHW-044/045** (Speculos screen authoritative / "cached" display string — both about display fidelity of values that ARE device-shown; here the address is NEVER device-shown at onboard). Distinct from **AHW-079** (pre-reveal pseudonym from the approval-free pubkey — a privacy-linkage finding, not an address-attestation forgery). The index's confirmed-clean "the 'verified on device' address pill IS genuinely device-attested" is scoped to "transfer/drip via B3 … onboard via device-revealed secret" — this finding shows that "onboard via device-revealed secret" attests the SECRET, not the ADDRESS, so the negative does not cover the receive-identity surface. Novel.

### F-J-2: The signing pubkey that defines the account is fetched approval-free from THREE independent provider instances with no cross-consistency check; a selective-MITM transport can feed a different pubkey to the address-deriving call than to the cache-key/ctor call
- Severity: MED — a MITM/compromised transport that returns a DIFFERENT pubkey to the cache-key probe vs the constructor-arg probe makes the cached secret, the displayed address, and the deployable account mutually inconsistent with no host detection; fail-closed only LATER at deploy (device 0x6F0E/0x6F0F) or never (already-deployed path), so the host trusts an unverified, inconsistent key as the account identity.
- Owned: OURS
- Category: WIRE
- Location: `onboarding.ts:77-83` (`deviceCacheKey` constructs a FRESH `LedgerProvider` and calls `getPublicKey`), `auth-witness-provider.ts:79-89` (`getPublicKeyXY` is a SEPARATE provider instance, separately caches `cachedXY`), `account-contract.ts:41` (deploy ctor args pull `getPublicKeyXY()`), `aztec-ledger-session.ts:64` + `OnboardPanel.tsx:64` (the cache-key probe), `provider.ts:64-76` (`getPublicKey` — length-checked, never verified against anything).
- What: The signing pubkey `x‖y` is the account's cryptographic identity (it's a constructor arg → folds into the address). At onboard it is fetched approval-free at least twice from two DIFFERENT `LedgerProvider`/provider instances: once by `deviceCacheKey()` (its own `new LedgerProvider(transport)`) to key the secret cache, and once by `getPublicKeyXY()` (the account-contract's provider, with its own `cachedXY`) to build the ctor args / address. Nothing asserts these two reads returned the SAME bytes, and nothing verifies either against the revealed secret (they're independent device outputs). The host treats the first `getPublicKey` it gets as ground truth.
- Attack/impact: A MITM transport (or compromised `@ledgerhq/*` shim — F-C-3/AHW-087 already note the transport is unverified) can return pubkey **A** to `deviceCacheKey` (so the cache key looks stable / matches a prior session) but pubkey **B** to `getPublicKeyXY` (so the address pill + deployable account bind to B). Or it can simply return a fabricated pubkey to the address-deriving call. Because `getPublicKey` is approval-free and never `secp.verify`'d against the secret or against a second read, the host derives + displays an address for a key the device may not control. This fails closed only if the user reaches Deploy (the device re-derives pkh+address from ITS pubkey and rejects, 0x6F0F) — but the already-deployed path (F-J-1) skips Deploy, and the receive flow never signs. Compounds F-J-1: the inconsistency gives the attacker a second lever (split the identity the cache trusts from the identity the address shows).
- Evidence: `onboarding.ts:81` `const pk = await new LedgerProvider(transport).getPublicKey(bip32Path);` (a throwaway provider, distinct from the contract's); `auth-witness-provider.ts:83-87` builds its OWN `getPublicKey`/`getSchnorrPublicKey` result into `cachedXY`; no code path compares the two, and `provider.ts:64-76` returns the bytes after only a 64-byte length check. There is no `secp.verify` or pubkey↔secret consistency check anywhere (consistent with the index's open AHW-087 sig-verify gap, but that's about the SIGNATURE; this is the PUBKEY/identity read).
- Fix sketch: fetch the pubkey ONCE and thread the single value to both the cache key and the ctor (single source, like the bip32Path single-source discipline at `aztec-ledger-session.ts:231-238`); and/or have the device attest the pubkey→address binding on an approval surface (see F-J-1's `GET_AZTEC_ADDRESS`), so a per-call pubkey swap can't survive. At minimum assert the two reads are byte-equal before trusting either.
- Confidence: high
- Dedup-check: distinct from **AHW-087/F-C-3** (host never `secp.verify`s the returned SIGNATURE vs cached pubkey — that's the signing path; this is the unverified/duplicated PUBKEY READ that defines the account identity). Distinct from **AHW-079** (privacy pseudonym of the pubkey). Distinct from **AHW-064** (path-length gate on the pubkey getters). Novel.

### F-J-3: `OnboardPanel`/`ConnectPanel` assert a host-controlled "Device verified" / "✓ Viewing keys derived on-device" state with no device-attested anchor — the same authority-implying UX the project's own anti-phishing rule forbids on the address pill
- Severity: LOW — UX/anti-phishing inconsistency, not a crypto break by itself, but it manufactures the trust impression that F-J-1 then exploits.
- Owned: OURS
- Category: APP
- Location: `ConnectPanel.tsx:127` ("Device verified. …" — printed after only `getVersion()`), `OnboardPanel.tsx:197-198` ("✓ Viewing keys derived on-device."), contrast the explicit rule in `style.css:5-12` + `:391-393` ("this file MUST NOT add host-rendered 'verified' badges … only the device screen is authoritative").
- What: The CSS carries a deliberate anti-phishing rule: the host must never render a "verified" badge/checkmark implying host authority over a value, because only the device screen is authoritative. But the React panels do exactly the spirit of that: `ConnectPanel` prints "Device verified." after a bare `getVersion()` (which proves only that *an* Aztec app answers an unauthenticated APDU — see AHW-080, app-presence is not identity), and `OnboardPanel` prints a green "✓ Viewing keys derived on-device." status. Neither claim is bound to a device-attested value the user can independently confirm except the secret checksum (which, per F-J-1, doesn't certify the address). The text-vs-badge distinction is cosmetic; the user reads "verified / on-device ✓" as endorsing the whole panel, including the address pill beside it.
- Attack/impact: no direct exploit, but it is the social-engineering substrate for F-J-1: the user is primed by host-rendered "verified/✓ on-device" language to trust host-rendered values (the address) that the device never attested. The project already recognized this risk for the address pill specifically; the same discipline isn't applied to the surrounding status copy.
- Evidence: `style.css:5-12` states the rule; `ConnectPanel.tsx:121-130` renders "✓ Connected" + "Device verified."; `OnboardPanel.tsx:198` "✓ Viewing keys derived on-device." The only genuinely device-attested onboard value is the secret checksum, and even its copy ("should match the device screen", `:203`) doesn't scope what it certifies.
- Fix sketch: scope the copy to what's actually proven ("App responding" not "Device verified"); drop the standalone green ✓ on onboarding unless it's tied to a device-attested address fingerprint; explicitly tell the user the ADDRESS is not device-confirmed until they approve a deploy/transfer on the device.
- Confidence: high
- Dedup-check: distinct from **AHW-054** (on-DEVICE "(verified)" halo over-scope) — that's the device screen; this is HOST-rendered status copy. Distinct from **AHW-044** (Speculos panel authoritative). Adjacent to F-J-1 but separately fixable (copy vs the missing attestation). Novel.

## Confirmed clean — tried to break, could not (auditor-facing negatives)

- **SEND-side address binding is genuinely device-attested (the prior confirmed-clean HOLDS):** for transfer/drip the device re-derives the account from (profile_id, salt) and binds `consumer` via `b3_verify_consumer_is_this_account` (fail-closed 0x6F12); for DEPLOY the device re-derives pkh+address from its OWN secret and rejects host mismatch (`begin_deploy_account.c:150-153` reads `expected_address`, `finalize_deploy_and_sign.c:174-183` re-derives `p6_addr` and `ct_memcmp32`s it vs `address_local`, signing only on equality). The deploy review shows the DEVICE-derived `address_local`, not the host claim (`deploy_review_ui.c:104-105`). I could not make the device sign a transfer/deploy for an address it didn't itself derive. (Note: D-codex's F-D-1 flags a post-review fault-window TOCTOU on the deploy path; orthogonal to the no-fault binding, which holds.)
- **The revealed secret IS device-derived + integrity-checkable:** the device hashes the PRIVATE child key (`get_aztec_master_secret.c:9`, `aztec_secret.c`), derives twice + `ct_memcmp32` before arming (fault-hard, `:137-153`), and the 16-bit checksum lets the user catch a TYPO/transport-corruption of the secret bytes. The reveal is human-gated. The secret↔checksum relationship is sound — it just doesn't extend to the address (F-J-1).
- **No attestation REPLAY across the signing paths:** the signed outer_hash binds (addr, chainId, version, payloadHash incl. txNonce); the device witness is one-shot keyed by canonical `messageHash` (`clear-signing-entrypoint.ts:243-252`, `#pending` nulled on read); deploy self-protects via the constructor init-nullifier and public tx via the cancellable nonce nullifier (AHW-049 fix, `session-embedded-wallet.ts:123`). A recorded FINALIZE response is a 64-byte sig over a specific hash — replaying it only re-asserts the same already-known authorization, not presence for a new intent. No cross-account/cross-session signature reuse window found beyond the (separately tracked) replay-billing residue AHW-049.
- **Cached re-onboard does NOT trust prior device state in a forgeable way:** the secret cache is memory-only (`secret-cache.ts`, grep-clean of storage — re-confirmed by Agent C), keyed by the device signing pubkey per path (`onboarding.ts:77-83`), so a different device/index is a cache MISS → fresh reveal. Cache "poisoning" of `getPublicKeyXY`'s `cachedXY` is per-instance in-process only (no shared/persisted cache to poison cross-origin). The cached-re-onboard weakness is the address-attestation gap (F-J-1) + the dual-read inconsistency (F-J-2), NOT a poisonable persistent cache.
- **`provider.ts` device-response parsing is uniformly exact-equality + fail-closed:** 64B pubkey, 64B sig (r‖s), 32B secret (`FR_BYTES`), 3B version, 4B caps — every length is `!==`-checked and throws; `encodePath` strictly rejects empty/over-long/non-uint32 components. `Fr.fromBuffer` (onboarding.ts:54) asserts `< MODULUS` (canonical-secret invariant). A MITM feeding bad lengths/SWs fails closed (= AHW-011 scope). The residual MITM levers are the unverified-pubkey-read (F-J-2) and the missing sig-verify (AHW-087) — both already captured.
- **No host-driven path weakens M8 device-derived sovereignty for SEND/DEPLOY:** the device owns address/pkh derivation on every path that SIGNS; the host cannot make the device sign for a host-asserted address. The sovereignty erosion is confined to the onboard/receive surface that never signs (F-J-1), where "sovereignty" was never actually enforced — only displayed.
- **Reveal scope / persistence not re-litigated:** AHW-047 (privacy-root scope) and AHW-048 (no longer persisted) are correctly tracked; I found no NEW host path that broadens what reveal exports or re-persists it.
