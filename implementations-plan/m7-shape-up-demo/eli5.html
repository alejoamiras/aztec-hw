Why we're doing this

Today the demo works end-to-end — you can deploy an Aztec account, drip USDC, and transfer it, all on alpha-testnet, with the device showing a real review screen for the drip and transfer.

But three things make it feel rough:

  • Deploy is blind-signed. The device shows you a 32-byte hash and asks you to trust it. You can't see what you're approving.
  • The timeline lies. Click Deploy and the progress header jumps to "Submit" while the device is still waiting for your approval. The progress bar is reading tea leaves (regex on label strings) instead of being told what's actually happening.
  • The visual style is rough. Spacing, typography, motion — looks like scaffolding, not product.

The three pieces

1 · Clear-sign deploy. The device shows you the account address it's about to deploy, plus the path and fee-payer, and signs only after you approve. Same security pattern as the existing drip + transfer clear-signing.
2 · Structured timeline. The adapter tells the UI exactly which phase it's in. The UI stops guessing. Deploy joins the same 9-phase pipeline that drip and transfer use.
3 · CSS polish. Same vanilla CSS file; tighten type/spacing/motion/hierarchy. ~80 lines net diff. No framework migration.

Order matters: deploy → timeline → polish. Polish ships last so it can't paper over the timeline bug behind nicer typography.

Clear-signing the deploy, explained

What the device does today

You click Deploy. The browser computes a 32-byte hash of the entire deploy transaction (called the outer_hash) and sends it to the device. The device displays:

Sign Aztec outer_hash? outer_hash: 0x9a3c...4f1b [Confirm] [Reject]

The user has no way to know what they're signing. Could be deploying their account, could be authorizing a malicious transaction. The hash is unreadable.

What the device will do after M7

Deploy your Aztec account? Address: 0x014ca15c2cc16501246e710534c87ef 20cfce682f0efaaa4bb970ecf547f2771 Path: m/44'/0'/0'/0/0 Fee paid by: testnet sponsor Class: EcdsaKAccount v1 [Confirm] [Reject]

The user reviews the address and the BIP-32 path; if they expected to deploy at this address from this key, they approve.

The honest part

What the device can verify cryptographically: the BIP-32-derived signing pubkey, the initialization hash, the salted init hash, the partial address — all the way up to the next-to-last step in the Aztec address derivation.

What it can't verify in this arc: the final step is an elliptic-curve operation on the Grumpkin curve. The Ledger SDK doesn't ship Grumpkin scalar-multiplication, and writing it from scratch is ~2 weeks of work. So the final address is shown, but not independently recomputed by the device.

What that means in practice: a malicious browser can deploy a valid account whose protocol keys (the encryption keys for incoming notes) the host controls. The deploy will succeed. The user thinks they own it. But the host can read every incoming note. This is a privacy attack the user authorized unknowingly, not just an availability blip. The user's signing key (held in the Ledger) is still safe, so funds can't be stolen — but transaction privacy is broken if the host is malicious. We document this honestly; the Grumpkin lift + a BIP-32-derived protocol secret (both M8) close the gap.

How we built it (briefly)

  1. Bypass the framework's DeployAccountMethod — turns out it signs during request assembly, before we'd have a chance to intervene. So we build the deploy payload manually.
  2. Build the initialization payload + the sponsor fee payload separately.
  3. Send a new APDU to the device with the address, salt, public_keys_hash, etc. Device shows the review screen.
  4. User approves. Device signs the outer_hash with the same fault-hardened pattern as drip/transfer.
  5. Browser injects the signed witness and submits the deploy tx.

Fixing the timeline lie

The old approach: when the adapter wanted to update the progress bar, it called onStep('Submitting deploy tx…') with a free-text label. The UI then ran a regex over the label to guess which phase to highlight ("submitting" → phase 4 of 6). Wrong on deploy because the framework calls "Submit" while the device is still on the Sign screen.

The new approach: onStep('sign', 'Awaiting deploy approval on device…'). The phase is the source of truth. The label is for human eyes only.

And because clear-signing the deploy means deploy goes through the same 9-step recipe as drip and transfer, ALL THREE actions have an identical phase sequence — the timeline shows the same six markers and lights them up in the same order.

Visual polish

~80 lines net diff in style.css. Highlights:

  • Type scale: tighten the existing ad-hoc font sizes onto a consistent ramp.
  • Neutral ramp: add elevation tokens so the status bar can lift visually above panels.
  • Connector bug fix in the phase timeline — the existing line uses left: 60%; right: -40% which overshoots on narrow viewports. Replace with calc'd offsets that hit the next marker's center reliably.
  • Finite, not infinite, pulse animation. Infinite pulses on signing screens are a phishing pattern. Change to 3 cycles then settle.
  • Button press feedback, address pill with copy-on-click, panel hierarchy tweaks.
  • Anti-phishing discipline: no host-rendered "✓ Verified" checkmarks anywhere. The device screen is the only authoritative surface.

Contested decisions to reconfirm

Both codex (xhigh) and the opus subagent pushed back on two of the earlier user choices. Worth a second look before locking:

Contested Address-only display on device.
Both auditors say: also show the BIP-32 path and the fee-payer. Reason: path mis-selection is a cheaper attack than breaking secp256k1. An attacker who can suggest the path (e.g. via a malicious dApp prompt) doesn't need to break crypto — they need to get you to sign at a different path. Showing the full path makes that visible.
Contested Address truncation length.
6 leading + 4 trailing hex chars = 40 bits. Vanity-brute-forceable in minutes. Both auditors recommend full 64-char address on the one-time deploy review (NBGL supports scrolling).
Contested Grumpkin EC on device.
Without it, "device shows truth" has the gap above. Codex sketched the full chain. Opus and the consolidated plan recommend punting to M8 because the lift is ~2 weeks. Worth confirming you're OK with that trade.

What we're punting to M8 (and why)

Things that came up in adversarial review but didn't make the cut:

  • M8 Grumpkin scalar mult on device. Lets the device verify the FULL address derivation. ~2 weeks of new crypto code. Real production design.
  • M8 INS_GET_AZTEC_SECRET. Currently the host generates secret = Fr.random() per session and derives publicKeys from it. Opus pushed: lift to BIP-32-derived secret. Real production design; ~1 week.
  • M8 Independent crypto oracle. Right now our host TS poseidon2 and device C poseidon2 are tested against same-repo golden vectors. A shared bug would silently survive. Need at least one external vector source (barretenberg or Noir-derived).
  • M8 Typed MessagePort for onStep. Closure callback works fine for v0; for production tightening, replace with MessagePort so a browser extension can't interpose.
