## Differential-replay gate — codex design review (session 019e80a6, xhigh) + oracle build
**Verdict: sound-with-changes.** Codex found one real false-negative the corpus-only design would have missed + 4 lesser issues. All folded:
1. **[Critical] Reject reservoir.** libFuzzer's on-disk corpus is COVERAGE-minimized — it keeps coverage-interesting inputs, NOT a representative reject sample. The exact "host-rejects / device-accepts" class the gate exists to catch can be ABSENT from the corpus → corpus-only replay = theater. **Fix:** `reservoir.{h,c}` — an env-gated (`WIRE_RESERVOIR=<dir>`) stratified harvester keyed by (emitted SW, length-bucket), cap 12/bucket, zero-overhead when unset. Harvested during the re-run: authwit 229 / append 109 / deploy 313 samples, stratified across every reject SW each handler emits (verified via `replay_* | uniq -c`).
2. **[High] Deploy accept bucket too broad.** After a parse-accept the device returns only {0x9000, SW_HASH_MISMATCH 0x6F01, SW_DEPLOY_PUBKEY_HASH_MISMATCH 0x6F0F, SW_DEPLOY_ADDRESS_MISMATCH 0x6F0E, SWO_UNKNOWN}. Allowing SWO_UNKNOWN/0x6F01 in the accept bucket is too loose (internal-fault SWs, not semantic variance). Narrow to **{0x9000, 0x6F0F, 0x6F0E}**; a 0x6F01/SWO_UNKNOWN on replay = investigate. Also: a parse-valid seed is NOT device-valid (the device checks pkh/addr vs its own seed → 0x6F0F for a random input) — need ≥1 truly device-valid deploy seed for the →0x9000 path. (deploy corpus already has 13 parse-accepted inputs; device will answer 0x6F0F for those.)
3. **[Medium] append session-seed was unreproducible.** The harness seeded `consumer=0xC0…` (top byte 0xC0 ≫ Fr-modulus top 0x30 → NON-canonical → `begin_authwit.c:76` would reject it). **Fix:** reseed canonical `0x0C…`; a real BEGIN_AUTHWIT (`call_count=1` → `state=HEADER_PARSED, calls_received=0`, consumer set verbatim) now reproduces the session exactly → append replay can assert EXACT SW. append reads only {state, call_count, calls_received, consumer} so matching those four suffices.
4. **[Medium] Cap body at 255.** Speculos frames a one-byte Lc (`speculos-transport.ts:129`); the device can't receive size>255. `run_one` now caps at `WIRE_MAX_LC=255` (260B backing array kept for over-read semantics).
5. **[Low] Slack poison.** `run_one` memsets the 260B buffer 0xAA before the body → deterministic oracle + diverges from the device's stale-tail content (an over-read past Lc → different SW → caught). Defense-in-depth (the vendored buffer is bounds-checked).

**Oracle:** each `fuzz_*.c` now exposes `uint16_t run_one(data,size)` (shared by the libFuzzer entry + the replay binary, so replay measures EXACTLY what was fuzzed). `replay_main.c` (no `-fsanitize=fuzzer`, ASan/UBSan on) reads each input file → prints `<basename> <sw>`. `make replay-all`. All 3 fuzz targets RE-RAN clean under the hardened harness (300k/400k/1M, cov 106/137/170, ZERO crashes).

**Stale-comment fix found incidentally:** `sw.h` called SW_DEPLOY_PUBKEY_HASH_MISMATCH/ADDRESS_MISMATCH "reserved: fires when M8 Grumpkin EC lift lands" — but `begin_deploy_account.c:303/308` returns them on every deploy (M8 P6 wired the check; the lift landed M8 P3). Comment corrected.
