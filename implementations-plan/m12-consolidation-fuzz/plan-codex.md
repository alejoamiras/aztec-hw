- Approach: fuzz the handlers directly, not the dispatcher. Existing dispatcher tests already cover CLA/INS/P1/P2, and the chosen handlers do not enter NBGL or signing, which keeps the shim tractable. Compile the real handler C plus the real `clear_signing_v0` tables, `args_hash`, `fr_canonical`, session code, and the real crypto/l4 code needed by deploy-begin; shim only `buffer_t/read_*`, `io_send_sw`, `explicit_bzero`, and the BOLOS derivation/hash calls. This is the real M12 lift; “moderate” is optimistic.
- Corpus: seed from the current negative cases, but negative-only is not enough. Add at least one canonical valid seed per target, including K1 and Schnorr deploy-begin, or coverage will plateau in the early rejects and miss the deep state/crypto paths.
- Gates: `make -C ledger-app/tests/wire_host smoke`; ASan+UBSan libFuzzer runs to local coverage plateau; then rerun the real-device `wire-negative.test.ts`. Any sanitizer-found bug gets fixed and followed by the existing deploy/provider/e2e lanes relevant to the touched code. Not CI this arc.
- Risk/rollback: the shim can diverge from BOLOS and either hide real bugs or invent fake ones. That is acceptable only if the scope is explicit: this harness is a memory-safety and state-machine tool, not a semantic proof of device equivalence. Any interesting crash needs a second reproduction path before you treat it as a real finding.

**Security & Adversarial Considerations**
- The B3 consumer binding in [finalize_and_sign.c](/Users/alejoamiras/Projects/aztec-hardware-wallet-poc/ledger-app/src/handler/finalize_and_sign.c) stays untouched. No host-supplied `salt` or `profile` fields. No wire bump. No “just for fuzzing” weakening.
- P0 can drift semantically even if it looks trivial. The dangerous mistake is “while I’m here” cleanup: changing zeroization timing, switching which session global is read, or subtly altering the K1/Grumpkin dispatch.
- P2’s shim is the biggest false-confidence risk. The direct-handler choice limits divergence, but BOLOS derivation and SDK buffer semantics are still trust assumptions. Treat the harness as a bug finder, not as proof the real device is safe.
- P3’s measurements do not generalize automatically. A passing `fr_mul` prototype does not prove full `fr`+`fq` migration viability, and no host/Speculos timing result proves physical-device side-channel resistance.

**Sequencing**
- Keep the order `P0 -> P1 -> P2 -> P3`. P0 first shrinks the deploy blast radius before fuzzing; P1 is cheap and stabilizes host-side profile selection before deeper test work; P2 should run before P3 so sanitizer triage happens on the current arithmetic, not on experimental `cx` code.
- Signed checkpoints make sense as `safe-v15`, `safe-v16`, `safe-v17`, `safe-v18` on one `m12` branch.

**Adversarial Self-Critique**
- The plan is most likely wrong in P2 effort sizing. `begin_deploy_account.c` drags in enough crypto and BOLOS behavior that a sloppy shim will be worse than no shim. If that starts happening, stop and narrow the harness rather than pretending coverage exists.
- The second weak spot is P3 evidence quality. If the spike does not explicitly answer both moduli and default-build size/latency impact, the honest output is “insufficient evidence, accept residual for now,” not “M13 is greenlit.”
