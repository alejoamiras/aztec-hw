M12 — Consolidation & Fuzz

The plain-language companion to plan.md. No new features — this arc makes what we already built tidier, more tested, and more honestly understood.

Last arc (M11) hardened the signing crypto. This arc does three quieter things: remove duplicated code, point an automated bug-hunter at the place a malicious website attacks, and answer the one open crypto question with real measurements instead of a guess. Four small-to-medium steps, each checkpointed.

P0 — Tidy the deploy code safe-v15

What: merge two copies of the same code into one. Why: duplicated code rots — a fix lands in one copy and not the other.

When the device sets up a new account, two different files each contain the same little routine for "work out this account's address from my key." We collapse them into one shared, self-contained helper (you can hand it inputs and test it on its own — no hidden dependencies).

Like having the same recipe written on two index cards: eventually someone edits one and not the other, and now your cake is wrong. We keep one card.

The catch we're watching: this touches the code that decides which account a deploy creates. A subtle slip = deploying to the wrong account, silently. So the proof isn't a unit test — it's actually deploying both account types on the live test network and confirming the address is byte-for-byte the same as before.

P1 — Stop hardcoding a number safe-v16

What: read a value from the generated source of truth instead of typing it by hand. Why: a hand-typed number silently drifts out of sync.

The host software currently has a literal isSchnorr ? 1 : 0 to pick which account template to deploy. That number has to match a table the build generates. We make the host look it up by name instead — so if the table ever renumbers, the code stops compiling (a loud, safe failure) rather than silently picking the wrong template.

It's tiny, but it's a real safety improvement, not just neatness: a wrong number here could mean signing for the wrong kind of account.

P2 — Point a bug-hunter at the parser safe-v17

What: set up a "fuzzer" — a tool that throws millions of malformed inputs at our code looking for crashes. Why: that parser is exactly where a hostile website's data lands.

We're not building the fuzzer — it's a standard, off-the-shelf tool (libFuzzer + the AddressSanitizer). We're building the harness: the scaffolding that lets that tool run our real device code on a normal computer, plus a thin layer faking the few bits of the Ledger chip it needs.

This is the biggest piece of the arc, and it splits in two:

  • P2a — the two "pure parser" handlers (read a request, check it, accept/reject). These run on a computer faithfully and cleanly. This is where most of the attack surface is.
  • P2b — the deploy handler is different: it does real chip-crypto we can't fake honestly. So we fuzz only its parsing half and leave the crypto alone. (This needs one small refactor — see the decision below.)

The danger with fuzzing off-device: the fake layer might lie.

If our stand-in behaves even slightly differently from the real chip, the fuzzer either misses real bugs or invents fake ones. Three defences: (1) copy the chip's real input-reader verbatim (don't rewrite it); (2) size our buffer exactly like the device's; (3) replay anything the fuzzer accepts back onto the real emulator and confirm it agrees. Any crash gets fixed in the device code with a new regression test — never papered over in the fake layer.

Like crash-testing a car: worthwhile only if your test dummy and track behave like the real road. If the dummy is wrong, you "learn" things that aren't true.

P3 — Settle the last crypto question, with numbers safe-v18

What: a measurement spike that ends in a written decision — not a code migration. Why: decide with evidence, not a guess.

One tiny timing quirk remains: our big-number multiply finishes a hair faster on some values. In theory a very patient attacker with the physical device could read secrets from that. The big version of this was already fixed last arc; this is the subtle remainder, and the closest professionally-audited wallets (Mina, Zcash on Ledger) simply accept it.

So instead of blindly rewriting our math to use Ledger's built-in version (risky, maybe slow, maybe doesn't fit), we run a small experiment: wire it up for one operation, measure the real speed, confirm it actually removes the quirk and handles our number sizes — then write a decision with the numbers. The honest answer might well be "document it and accept it, like the peers do." That's a complete outcome.

Before re-plumbing the whole house, you test one tap. The result might be "the new pipes aren't worth it" — and that's a finding, not a failure.

⚠ The one decision we need from you

For P2b (fuzzing the deploy parser), we need to split that handler into a "parse" part and a "crypto" part, so we can test the parse part safely. That means editing a security-sensitive file — though only the parsing, never the part that checks "is this really my account?"

  • Option X (recommended): allow the parse-only split. We get real bug-hunting on the deploy parser; the security check stays byte-for-byte untouched; it's easy to undo.
  • Option Y (safe fallback): don't touch that file at all. We then only bug-hunt the other two handlers, and cover the deploy parser with the existing on-device tests.

If you don't weigh in, we proceed with X, and the plan is written so it cleanly falls back to Y.

What we are deliberately not doing

  • The actual crypto-math migration (that's a separate future arc, only if P3's numbers justify it).
  • Any change to the locked-down account binding (you ratified keeping it firmware-pinned last arc).
  • Wiring the fuzzer into CI; an external audit; new account types. All later.
Order: P0 → P1 → P2 → P3, one branch, a signed checkpoint tag per step. Full detail, validation gates, and the security analysis: plan.md.
