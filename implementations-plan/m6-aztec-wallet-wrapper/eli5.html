M6 — AztecLedgerSession + Browser PoC

A plain-language walkthrough of the plan to take what we already built (clear-signed signatures from a Ledger) and actually submit a real transaction on alpha-testnet, end-to-end, from a browser. Full plan.

The one-line story

Last week's work made the device sign Aztec transactions with decoded UI ("Transfer 1.5 USDC to alice"). What it didn't do is submit those signatures to the chain — because Aztec's wallet code has three small bugs that make hardware-wallet integration awkward. This arc builds a thin wrapper to work around those bugs and writes up the bugs as PR suggestions for the Aztec team.

What you'll see in the demo video

  1. Browser page at localhost:5173 with three buttons.
  2. Click "Connect" → Ledger (real or Speculos) shows its address screen.
  3. Click "Deploy account" → Ledger shows a hex hash, you confirm. Account exists on testnet.
  4. Click "Drip 1000 USDC into me" → Ledger shows "Drip USDC, Amount: 1000.0 USDC, To: you". You confirm. 1000 USDC appears in your account.
  5. Click "Transfer 100 USDC to alice" → Ledger shows "Transfer pub→pub USDC, From: you, To: 0xalice…, Amount: 100.0 USDC, Mode: PUBLIC". You confirm. 100 USDC arrives at alice.
  6. All three txs link to testnet.aztecscan.xyz.

So 4 protocol keys derive from one browser-held secret; only the signing key lives on the Ledger. The browser secret dies on page reload (no localStorage, no persistence). The Ledger key never leaves the device, ever.

Why a wrapper at all

Aztec's wallet.sendTx(...) does this internally:

  1. Build the call list (sponsor + your transfer)
  2. Generate a random txNonce
  3. Compute outer_hash from (calls + nonce + account info)
  4. Ask the provider: createAuthWit(outer_hash) — passing only a 32-byte hash
  5. Submit

Step 4 only knows how to ask for a hex hash. It has no concept of "show the user that this is a USDC transfer for 100 to alice." Step 2's random nonce means we can't pre-compute outer_hash to clear-sign.

AztecLedgerSession takes control

1. Build the call list ourselves (just like sendTx would)
2. Pick OUR OWN txNonce (no random surprise)
3. Compute outer_hash from those exact bytes
4. Pre-sign via clear-signing → device shows "Transfer 100 USDC..."
5. Build the tx request manually with our nonce + a "frozen-witness
   provider" that hands the framework exactly the pre-signed authwit
6. Submit to PXE

Phases

Add Wonderland's Dripper to the on-device registry (one new slot). Also: fix a SponsoredFPC address bug — the M5 manifest pins the local-sandbox address, not the alpha-testnet one. Without this fix every sponsored testnet tx would reject.

So the same Ledger code works against Speculos (emulator) and a real device. Also clean up an old type-cast that doesn't work in browsers.

Thin subclass of Aztec's EmbeddedWallet (in-browser PXE+prover). Exposes the helpers our wrapper needs without dirty casts.

The AztecLedgerSession class. The clear-signed transfer recipe. The FrozenAuthWitnessProvider (one-shot, hash-asserted — throws loudly on mismatch).

The four lessons for the Aztec team

  1. Let callers supply txNonce to sendTx. One-line change in base_wallet.ts:180. Unblocks every "pre-sign offline, submit later" pattern — hardware wallets, sponsored relayers, multisigs.
  2. Optional createAuthWitFromIntent on AuthWitnessProvider. Lets hardware wallets receive the structured calls instead of just a hash — so they can actually clear-sign without re-implementing entrypoint encoding.
  3. opts.presignedPayloadAuthWitness on sendTx. First-class "I already signed this, just use it" path. Mirrors what EVM ecosystems painfully evolved to (Safe, ERC-2771 sponsored relayers).
  4. Re-export outer_hash preimage helpers. computeOuterAuthWitHash and EncodedAppEntrypointCalls are currently framework-internal. Wallet integrators (us, plus everyone after) burn ~5 days re-implementing them and verifying parity. Zero internal change; saves the next integrator the work.

What's deliberately NOT in M6

  • Private transfers — opens private-note scope; reserved for M7.
  • Token approve/spend — only own-account flows in v0.
  • Multi-call (manifest with >2 calls) — sponsor + 1 user call is the only shape.
  • Frontend audit hardening — CSP, SRI, origin pinning. Production concerns.
  • Schnorr-Grumpkin — still audit-gated, separate L5 effort.

What can still go wrong (and we're OK with)

  • Testnet flakes during the recording window — schedule a buffer day.
  • PXE first-sync can take minutes on alpha-testnet — we show a progress UI; if it dominates the video runtime we pre-sync off-camera.
  • WebHID + Safari = no — Chrome/Edge only. Document the requirement.
  • Wonderland redeploys Dripper to the same address with new code — caught by the M6.0 fail-closed getContractMetadata check.
