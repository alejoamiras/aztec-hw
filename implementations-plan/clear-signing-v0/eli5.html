Clear-Signing v0 — ELI5

A short, plain-language walkthrough of the plan to make the Aztec Ledger app show you what you're signing — not just a hex hash. Full plan.

What we already shipped (L4)

The Ledger app already does two non-trivial things, as of last week's work:

  • It computes Aztec's outer_hash on the device itself, so a malicious host can no longer trick the device into signing a different value than what it shows you.
  • It signs with ECDSA-K1, and the resulting signature is byte-equivalent to what Aztec's in-circuit verifier checks. We proved this against the real barretenberg verifier.

But the screen is still raw hex. The user sees Target 0x2af7…47c5, Selector 0xa9059cbb, Mode PUBLIC. Power-users can verify; nobody else can.

What clear-signing v0 actually does

The device gets a small built-in library of known Aztec tokens (USDC, ETH from your faucet) and a list of known FT actions (transfer, mint, etc.). When the host streams a transaction, the device:

  • recomputes the transaction's args hash from the raw arguments (no more trusting the host's claim),
  • looks up the contract in its built-in registry,
  • looks up the function in its built-in selector table,
  • renders something the user can read: "Transfer 1.500000 USDC, From: you, To: 0xabcd…ef12".

If anything doesn't match — unknown contract, unknown function, wrong number of arguments, wrong privacy mode — the device refuses to sign. No raw fallback inside clear-signing. (You can still blind-sign via the old INS for unusual cases.)

Why strict-allowlist (not graceful fallback)?

A wallet that says "Unknown contract — signing anyway" trains users to ignore warnings. If the v0 scope is "FT clear-signing", then anything that isn't FT should be a hard "no" so the UX has integrity. When we want more contracts supported, we add them to the manifest and rebuild — which is also when a human reviews them.

Important: the registry is hardcoded at build time. Adding a token means a firmware rebuild and reflash. That's the trust root.

Phases

M5.0 — Manifest freeze + codegen

Write a JSON manifest with the 5 known contracts (USDC, ETH, SponsoredFPC, 2 reserved) and 7 verbs (4 transfer variants + 2 mint variants + sponsor). A script reads this and emits C tables for the device + TS tables for the host. CI fails on drift.

M5.1 — Wire format v2

The "APPEND_CALL" APDU grows to include raw args alongside the args hash. New protocol version number so old hosts can't accidentally talk to new firmware (or vice versa).

M5.2 — Device-side parity + strict gates

Device recomputes args hash from raw args. Rejects if unknown contract, unknown function, arg count off, public/private mismatch, or (for transfers) "from" isn't the user's own account. Three independent recompute passes — same fault-hardening pattern as the existing outer_hash.

The most important invariant: after this lands, the device never trusts a hash the host claimed — it always recomputes from raw args.

M5.3 — Semantic UI

Replace the per-call hex display with: "Transfer 1.5 USDC, From: you, To: 0xabc…def". Decimals come from the on-device registry, never from the host. Mint operations show a yellow warning because they're privileged.

M5.4 — Host adapter

The TypeScript code that builds the transaction now streams raw args too. Unblocks the private-call path (currently rejected). Adds host-side pre-flight checks so obviously-bad requests fail before hitting the device.

M5.5 — Sandbox end-to-end test

Local Aztec sandbox + Speculos. Deploy a Ledger-backed account. Sign a real private-USDC transfer. Assert it lands. Validates the entire pipeline before we touch a public network.

M5.6 — alpha-testnet (the decisive test)

Same flow against rpc.testnet.aztec-labs.com with the real deployed USDC. The success criterion: a private USDC transfer signed by the Ledger via clear-signing gets mined on alpha-testnet.

M5.7 — Codex post-impl review + fixes

Send the full implementation back to codex for an adversarial review. Apply BLOCKERs and MAJORs.

What this costs (timeline-wise)

~12-14 working days. Codex flagged that M5.1+M5.2 are one chunk (you can't separately ship a wire format without the recompute logic), and the testnet work is denser than it looks (note sync, helper-wallet funding, etc.).

What we're not doing

  • NFTs — different ABI shape. Follow-up arc.
  • Arbitrary dApps — Aztec has no canonical contract registry yet. Trying to fake one would be worse than not having one.
  • Schnorr-Grumpkin — the "native Aztec sig" arc. Audit-gated, deferred until after this ships.
  • Ledger Live submission — much higher bar, separate ~$30k effort, not in scope.

The trust roots, plainly

  • The Poseidon2 implementation on the device — already shipped (L4.1), 14/14 parity vs Aztec.
  • The on-device contract registry — compiled into the firmware. Whoever builds the firmware is trusted to put the right addresses + decimals in.
  • The selector table — derived from canonical function signatures at codegen time. CI fails if the signatures drift against the pinned aztec-standards package.
  • The signature itself — ECDSA-K1 from a key the device derives from its seed via BIP-32. The seed is the user's secret.

The thing the user has to trust beyond their own seed: the firmware bytes are what the build pipeline produced, and the build pipeline used the manifest that was reviewed.

Open questions resolved during planning

  • SponsoredFPC address on testnet? Deterministic from SPONSORED_FPC_SALT=0: 0x254082…1257. Same address on mainnet, testnet, sandbox.
  • Sponsor is public or private? PRIVATE. Codex caught this — we had it wrong initially. Aztec's SponsoredFeePaymentMethod builds it as a private entrypoint.
  • Who pays for the first deploy? SponsoredFPC. No external ETH wallet needed for gas.
  • What's "FT"? Fungible Token. ERC-20-equivalent on Aztec. The aztec-standards Token contract by Wonderland.
