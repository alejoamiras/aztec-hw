# Clear-signing v0 — M5.0..M5.5 lessons

## Verdict
End-to-end clear-signing flow works on Speculos against the user's faucet
USDC contract. Device renders semantic fields (Transfer pub->pub USDC, From:
you, Amount: 1.5 USDC, Mode: PUBLIC) instead of selector hex. Signature
verifies under Aztec barretenberg Ecdsa.verifySignature. 74 tests pass.

## Key gotchas

### 1. Aztec selectors include the PrivateContextInputs param for private functions

Naive: "I'll just compute the selector from `transfer_private_to_public(AztecAddress,AztecAddress,u128,Field)` — 4 args."

Reality: aztec.js `FunctionSelector.fromNameAndParameters(name, params)` uses the artifact's full `abi.parameters` array, which for private functions has a prepended `inputs: PrivateContextInputs` field. So the actual signature being hashed is `transfer_private_to_public((Field),(Field),(Field),u128,Field)` — 5 args, where the first `(Field)` is the inputs context (struct wrapping a single Field).

This produces a DIFFERENT selector than the naive 4-arg signature:
- naive: `0xaf28c76f` (wrong)
- artifact-canonical: `0xd4fcf9f6` (correct)

The codex final-review BLOCKER #2 ("artifact cross-check must be fail-closed on shape mismatch, not warning-only") explicitly required catching this. The codegen script in `packages/adapter-ledger/scripts/gen-clear-signing-v0.ts` cross-checks selectors against compiled artifacts and FAILS the build on drift. Caught this exact bug during initial manifest writing.

**Lesson**: never trust hand-written function signatures for selector computation. Read the compiled artifact's parameter list, compute the selector that way, and pin it as a literal in the manifest for review. Then have CI assert the artifact still produces that selector.

### 2. SponsoredFPC.sponsor_unconditionally is PRIVATE, not public

Looking at the function name and the SponsoredFPC's purpose, the natural assumption is "public function — anyone calls it to get sponsored." Wrong. Aztec's `SponsoredFeePaymentMethod` (aztec-packages/yarn-project/aztec.js/src/fee/sponsored_fee_payment.ts:23-34) constructs the call with `type: FunctionType.PRIVATE`.

If we'd marked it `is_public: true` in the manifest, every sponsored deploy/transfer on alpha-testnet would have failed: the device would compute the args_hash via the wrong separator (PUBLIC_CALLDATA instead of FUNCTION_ARGS) and reject with SW_HASH_MISMATCH.

Codex final-review BLOCKER #1 caught this before code landed. Cross-check is now both selector + arg_count + visibility (was selector-only before).

**Lesson**: don't infer visibility from the function name. Read the artifact's `custom_attributes` (Token contract: "abi_private" / "abi_public") OR the canonical wrapper in aztec.js's fee payment (SponsoredFPC: `FunctionType.PRIVATE` literal).

### 3. computeVarArgsHash returns Fr.ZERO for empty args, not a hash

For private-call args_hash, the rule is `poseidon2HashWithSeparator(args, FUNCTION_ARGS)` — except when `args.length === 0`, in which case it returns `Fr.ZERO` directly (yarn-project/stdlib/src/hash/hash.ts).

For the SPONSOR verb (0 args, private), the device must emit `Fr.ZERO` as the args_hash. The on-device `cs_compute_args_hash` has a short-circuit for this case; without it, signing any sponsored tx would fail args_hash parity.

**Lesson**: when porting hash construction, look for `if (length === 0) return ZERO` patterns. Match them exactly.

### 4. Nano S+ NBGL font lacks U+2192 (→)

Initial labels like "Transfer priv→pub" rendered as "Transfer privbpub" on the actual Nano S+ display. The Unicode arrow falls back to a substitution character.

Fix: use ASCII `->` instead. Labels now read "Transfer priv->pub".

**Lesson**: Nano S+ NBGL font is essentially Latin-1; anything outside ASCII / Latin-1 is suspect. Test on the actual device (or Speculos screenshot), not just bytes-in-the-event-queue.

### 5. The trusted-session invariant matters

Codex M5 final-review MAJOR #4 flagged this: the device APPEND_CALL handler initially STORED the host-claimed args_hash, and the finalize-time outer_hash recompute READ that stored value. If a glitch corrupted memory between the parity check and the final read, the device would have signed a hash derived from corrupted args_hash bytes.

Fix: after the parity check passes, OVERWRITE `slot->args_hash` with the device-recomputed value. The host claim never survives past APPEND_CALL. Finalize reads only device-authored data.

**Lesson**: "device verifies the host claim" is necessary but not sufficient. After verification, the host's claim must be DISCARDED — replaced with device-authored bytes, or marked unreadable. Otherwise a glitch attacker can revisit the host's bytes after the check passes.

### 6. Strict allowlist removes a whole class of attack surface

The codex thesis (v0 = "narrow FT intent verifier", not "best-effort decoder with fallback") felt heavy-handed at first. After implementing it, the trust model is dramatically simpler:
- Decoder bugs cannot corrupt what gets signed (decoder runs AFTER parity)
- Registry is .rodata; no host can inject a "USDC" label
- Unknown calls don't degrade silently — they're hard-rejected at APPEND_CALL

The strict-allowlist also makes the testnet acceptance criterion sharper: every call must be in the registry/decoder, or no signature happens. We know exactly what scenarios v0 supports, and exactly which ones need follow-up.

**Lesson**: when in doubt for a v0 PoC, prefer strict-reject over graceful-degrade. Graceful degradation trains users to ignore "Unknown" warnings; strict-reject forces deliberate scope expansion.

### 7. The Aztec wallet framework doesn't natively use IntentAuthWitnessProvider

The Aztec wallet's `sendTx()` → entrypoint → outer_hash → `provider.createAuthWit(outerHash)` path is the L2 blind-sign path. The `IntentAuthWitnessProvider` extension (our `createAuthWitFromIntent`) is only invoked when we call it manually from a script.

For clear-signing to be the DEFAULT signing path during a wallet.sendTx() call, the framework needs to:
- Build a CallIntent representation alongside (or as the source of) the outer_hash
- Route through `createAuthWitFromIntent` when the provider supports it

This is the Aztec SDK extension proposed in `architectures/02-clear-signing-interface.md`. M5.5/M5.6's testnet submission path needs either this extension OR a manual witness-attachment pattern. Codex is researching the cleanest aztec.js workaround.

**Lesson**: the wallet's "use the device" path is independent from the "produce a clear-signed witness" path. They look unified to the user but they're not. Plan for that gap when shipping clear-signing to production.
