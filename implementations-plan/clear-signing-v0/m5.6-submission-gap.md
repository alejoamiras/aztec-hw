# M5.6 — testnet submission gap

## Status
**Not landed in v0.** Codex consulted (session `019e65ef`); the upstream aztec.js
at pin `2770bcb` does not expose a clean path for submitting a tx with an
externally-supplied entrypoint payload `AuthWitness`.

Clear-signing v0 in this repo produces a **valid** Aztec auth witness for the
user's faucet USDC (signature verifies under barretenberg
`Ecdsa.verifySignature`, 14/14 host-parity vs Aztec). What's missing is the
plumbing to USE that witness in a real `wallet.sendTx(...)` against testnet.

## Why upstream aztec.js doesn't support this today

Three independent issues from the codex finding (all citations to
`/Users/alejoamiras/Projects/aztec-packages` at `2770bcb`):

1. **No `setAuthWitness` analogue for payload witnesses.** `Wallet` only exposes
   `sendTx`, `createAuthWit`, and `authWitnesses` arrays on payload/options
   (`yarn-project/aztec.js/src/wallet/wallet.ts:258`). `AuthWitnessProvider` itself
   has only `createAuthWit(messageHash)` — no intent slot
   (`yarn-project/entrypoints/src/interfaces.ts:62`).

2. **Framework always uses `createAuthWit(outerHash)`, never
   `createAuthWitFromIntent(intent)`.** `DefaultAccountEntrypoint` builds
   `messageHash = computeOuterAuthWitHash(...)` and calls
   `this.auth.createAuthWit(messageHash)`
   (`yarn-project/entrypoints/src/account_entrypoint.ts:131`). Our
   `IntentAuthWitnessProvider` extension is invisible to this path.

3. **Random `txNonce` blocks pre-signing.** `BaseWallet.sendTx` generates a fresh
   random `txNonce` internally
   (`yarn-project/wallet-sdk/src/base-wallet/base_wallet.ts:179`); the witness
   we pre-sign would target a different outer_hash than the one the framework
   computes.

## The smallest workable path codex outlined

1. **Frozen-witness provider**: a custom `AuthWitnessProvider` that holds a
   pre-signed `AuthWitness` and returns it from `createAuthWit(messageHash)` —
   asserting the messageHash matches what we pre-signed for. Built on the
   existing account-contract seam (`yarn-project/accounts/src/defaults/account_contract.ts:25`).

2. **Manual tx-request construction**: bypass `BaseWallet.sendTx()` (which
   generates a random `txNonce`). Instead call
   `account.createTxExecutionRequest(...)` with a fixed `txNonce` that
   matches the one used during pre-signing.

3. **Exact call-list reproduction**: codex confirmed our `buildL4Manifest`
   matches Aztec's `EncodedAppEntrypointCalls.create(...).hash()`
   byte-for-byte (`yarn-project/entrypoints/src/encoding.ts:74`). For a
   sponsored transfer, the call list MUST be
   `[sponsor_unconditionally(), transfer_X(...)]` in that order — the sponsor
   is prepended via
   `mergeExecutionPayloads([feeExecutionPayload, functionExecutionPayload])`
   (`yarn-project/aztec.js/src/contract/contract_function_interaction.ts:97`).

4. **Submit through PXE directly**: use the same code path
   `BaseWallet.sendTx` uses internally, minus the random-nonce step. Prove
   the tx and send via PXE.

## Why M5.6 isn't shipping in this autonomous session

Two infrastructure prerequisites that cross the AFK threshold:

### A. PXE infrastructure

Aztec testnet doesn't expose a hosted PXE. The faucet's browser flow uses the
USER'S wallet PXE (e.g., Nulo browser extension). For a CLI submission we'd
need to:
- run a local PXE Docker container (`aztec start --pxe-only --aztec-node ...`)
- wait for it to sync (minutes)
- proxy our `Wallet` through that PXE

This is doable but is a separate piece of infra setup with its own pinning,
sync state, and error modes — not appropriate for autonomous overnight work.

### B. End-to-end account deploy + funding

The Ledger-backed account needs to be DEPLOYED on testnet before it can
sign transfers. The deploy itself is a sponsored tx that goes through
`provider.createAuthWit(outerHash)` (NOT our `createAuthWitFromIntent`) —
which means it'd be a blind-sign event on the device, not clear-signing.

That's fine in principle: the user blind-signs the deploy (one-time, hex
hash), then clear-signs transfers thereafter. But mechanically it still
requires the frozen-witness pattern for the deploy too, since the deploy's
outer_hash depends on a `secret/salt` + the framework's random `txNonce`.

Funding the new account with USDC also needs a HELPER non-Ledger account
on testnet (codex's recipe). That's another deploy + drip operation that
itself uses sponsored gas through the framework's normal path. Not blocked
by anything in our code — just a chain of operations that need careful
orchestration.

## What needs to land for full M5.6

1. **Local PXE setup**: Dockerised `aztec start --pxe-only` pointed at
   `https://rpc.testnet.aztec-labs.com`. Documented run command. Sync state
   handling.

2. **`LedgerWallet` wrapper**:
   - constructor takes `secret`, `LedgerEcdsaKAccountContract`, `salt`
   - exposes `deployAccount({ blindSign: true })` — uses framework's normal
     `sendTx` path (random nonce OK because deploy is a one-shot blind sign)
   - exposes `submitClearSignedTransfer(intent)`:
     1. Calls `usdcContract.methods.transfer_public_to_public(...).request({fee: sponsored})`
        to get the exact call list
     2. Picks a deterministic `txNonce` (e.g. `Fr.random()` — captured here)
     3. Builds CallIntent from the call list + txNonce
     4. Pre-signs via clear-signing flow (existing `createAuthWitFromIntent`)
     5. Wraps the resulting AuthWitness in a `FrozenAuthWitnessProvider`
     6. Calls `account.createTxExecutionRequest(...)` with the fixed nonce
        and frozen provider
     7. Proves via PXE, sends via PXE

3. **Helper account for funding**:
   - Schnorr-default in-memory account
   - Deploy via sponsored fee
   - Call Dripper to mint USDC to itself
   - Transfer USDC to Ledger account address (which only needs to exist
     in the address space, not be deployed yet)

4. **Integration test**: gated `bun test ... AZTEC_TESTNET_E2E=1`. Asserts the
   transfer lands `mined` and post-state shows the balance change.
