Pre-external-audit, I would treat this as a hardening pass, not a cleanup pass: no fallback paths, no “best effort” attestation, and no extra surface beyond the agreed W1–W7. The biggest mistake here would be solving the audit text while leaving the trust model soft.

**Phases**
1. **Protocol + config groundwork.** Land W2’s single-source sponsor config and W4’s wire contract first, because both change host/firmware assumptions. I would not use `MANIFEST_VERSION` for W4; I would add a new INS, a new `GET_CAPS` bit, and bump app version in `ledger-app/Makefile`. Host must hard-fail if the new capability is absent.
2. **Firmware state hardening.** Implement W1’s immutable reviewed snapshot + request-epoch invalidation before touching the new address INS, because the snapshot pattern is the right model for every approval-gated flow.
3. **Firmware feature work.** Add W4 `GET_AZTEC_ADDRESS`, then W2 deploy sponsor rendering, then W5 scrub cleanup. W4 and W2 both reuse deploy/account-derivation primitives, so they belong in the same code-reading window.
4. **Host integration + API lockdown.** Land W3 and the host side of W4 together: onboarding must stop trusting host-derived receive identity at the same time the raw blind-sign surface stops being a normal root import. W6 docs/UI can run in parallel here.
5. **Regression closure.** Finish W7 and update existing Speculos flows whose page counts/content changed. Validation gates are then the agreed docker firmware build + clean-port Speculos + `bun test`.

**Security & Adversarial Considerations**
- **W4.** Do not turn `GET_AZTEC_ADDRESS` into a generic attestation primitive. It should return only the address after approval, not a signed certificate blob. A signed blob is replayable, expands attack surface, and tempts host-side misuse; it does not improve the human comparison model. Also: exact `(curve_id, profile_id)` allowlist only, exact canonical path only, canonical salt only, separate opcode/capability bit, no fallback to host-derived address.
- **Does W4 really close AHW-098?** Yes, materially, if onboarding is forced through it. Today the device attests a secret while the host claims the address. After W4, the device authors the address itself and the host can only lie by hoping the user ignores the device screen. That is the same trust model as a hardware-wallet recipient confirmation, which is acceptable; the current checksum model is not.
- **W2.** Rendering the sponsor address helps, but it is not sufficient because users will not memorize an FPC address. The real control is single-sourcing plus fail-closed equality checks; the UI is the last line, not the only line. After this change there should be exactly one sponsor source: the clear-sign manifest/codegen input.
- **W1.** Separate immutable snapshot + compare-back fully removes the ordinary mutable-global TOCTOU and the `pk_info/sign_info` union-clobber path from the approval sink. It does not make arbitrary RAM faulting impossible; it forces the attacker to corrupt both the live state and the separate snapshot or the compare itself, which is the right app-level bar.

Phase breakdown: `P1 protocol/config`, `P2 firmware snapshot/scrub primitives`, `P3 W4+W2 firmware features`, `P4 host integration/API lockdown/docs`, `P5 regression + validation`.

Single biggest design fork/risk: **W4 compatibility and scope control**. If `GET_AZTEC_ADDRESS` becomes “just another derivation helper” or the host falls back when it is unavailable, the remediation is fake.
