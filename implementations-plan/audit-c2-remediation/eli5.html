Hardening the Ledger Aztec wallet — in plain words

Fixing the real problems an outside auditor will look for, before we hand it to them. Companion to plan.md · scope in scope.md.

A second deep review of the wallet turned up a pile of issues. We sorted them by how serious they are and walked through each one: fix it, or accept it and write down why. This page explains, with no jargon, what we're fixing and how.

The big picture

The wallet has two halves: the device app (code that runs on the Ledger and is the thing you actually trust — it shows you what you're approving and signs it) and the host library (TypeScript that runs in the browser and talks to the device). The golden rule: the screen on the device must match what the device signs, and the device — not the browser — must be the source of truth.

Most findings are variations on "the device signs or trusts something the user never really verified." We're fixing the ones that matter and documenting the rest.

What we're fixing

1. The "show one thing, sign another" gap HIGH device

When "blind signing" is on, the device shows you a value, you approve, and it signs — but it re-reads that value from a scratchpad after you've looked. A well-timed glitch could make it sign something different from what you saw. (The normal flows already avoid this; blind-sign was the exception. The deploy screen has a smaller version of the same issue.)

Fix: take a frozen photocopy of what you reviewed, sign that exact copy, and refuse if the live values changed. Build it once as a shared helper and reuse it. AHW-095 + AHW-099 (+ the reveal screen, AHW-112)

2. Your receive address was never proven by the device HIGH device + host

When you set up the wallet, the device proves it holds your secret — but the address you receive money to is worked out by the browser, and the device never shows or confirms it. A malicious browser could show you an attacker's address that still "checks out". (Spending is safe — that's already device-proven. This is the receiving side.)

Fix: add a new device command that makes the device itself compute and display your receive address for you to confirm — and have the browser refuse to continue unless its address exactly matches the device's. New command, gated behind a capability flag, no "skip it" fallback. This is the heaviest item. AHW-098

3. The public library handed out a "sign anything" tool HIGH host

Our published package exposed a function that signs any raw value, skipping the whole review screen. Any app using our library could call it.

Fix: take it off the front door — move it behind an explicit /unsafe path normal apps won't import. Also stop the package from letting other code silently re-read the revealed privacy key. AHW-097 + AHW-103

4. The deploy screen hid who pays the fee MED device

Deploying your account authorizes a "fee sponsor" contract to pay gas — but the screen just said "Sponsored (testnet)" and never showed which contract. (You correctly pointed out there's no single "official" sponsor to check against — so the fix isn't a check, it's showing it.)

Fix: show the sponsor's address + function on the deploy screen so you verify it, and make sure the browser and the device read that address from one single config so they can't disagree. AHW-096

5. A signing leftover could expose a key MED device

After a Schnorr signature the device wipes the private key — but leaves one intermediate value lying in memory that, combined with public data, reconstructs the key. Not readable today, but a future memory bug could harvest it.

Fix: wipe all the secret leftovers, not just the obvious ones. AHW-100

6. Two missing safety nets in the test suite MED

The device does reject bad inputs and does make non-malleable signatures — but no test checks it. A future change could quietly break either and every test would still pass green.

Fix: add tests that prove each rejection happens with the right error, and that signatures are the safe "low-S" form (this also closes a separate gap where the host never double-checks the device's signature). AHW-108 + AHW-109 (+ AHW-087)

7. The recovery docs described a wallet we didn't build MED docs

The design docs promised a "two independent secrets" backup model, but the code actually derives everything from the one Ledger seed. The docs would mislead an auditor about what happens if the seed is compromised.

Fix: rewrite the docs + UI to tell the truth — it's a single-seed model; the seed is everything; losing it strands the account. (We're not building the two-secret scheme.) AHW-106

Two decisions worth knowing

The new address command uses a "capability flag," not a version number. Both independent reviewers said: don't bolt this onto the existing wire-version; give it its own on/off capability the browser checks, and never let the browser quietly skip it. That makes "is the device proving the address?" a clear yes/no we can test.

"Sign the photocopy." The subtle but crucial part of fix #1: the device must sign the frozen copy of what you reviewed — comparing afterward is only a backup alarm, not the fix.

What we're not doing (and why)

  • Override seams (AHW-104) — dropped. Their danger came from the "sign anything" tool in fix #3; once that's gone, they can only drive the normal reviewed flow.
  • Double-read pubkey check (AHW-105) — dropped. Fix #2 (device proves the address) makes it unnecessary.
  • CI / build-pipeline hardening (AHW-101/102) — deferred to a separate release-gate pass (you've consistently parked CI).
  • Onboarding limited to 5 accounts (AHW-107) — deferred; the fix is in the front-end app, which is out of this round's scope.

Open questions / honest caveats

  • Fix #1's "refuse if changed" branch can't be honestly tested through the screen-scraping emulator — we'll budget a small device-level test harness to prove it.
  • Does fix #2 truly close the hole, or just move the trust? It closes it if setup is forced through the new command and the browser refuses on mismatch — the device becomes the source of truth. The one thing we can't fix: the user still has to actually read the device screen (true of every hardware wallet).
  • Poisoned builds are a bigger, separate problem (parked) — these fixes assume the firmware you flashed is the firmware we built.
