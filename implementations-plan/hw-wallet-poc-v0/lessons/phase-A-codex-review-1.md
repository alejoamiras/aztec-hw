**Findings**
1. The stock-firmware signing mode is wrong if you keep `aztec://...` as `identity.proto`. This is the biggest blocker. Your transport comment says `SignIdentity(proto="gpg")`, but [identity.ts](/Users/alejoamiras/Projects/aztec-hardware-wallet-poc/packages/adapter-trezor/src/identity.ts:30) builds `aztec://account/{i}`. In firmware, `sign_identity.py` decides the signed payload from `identity.proto`: only `gpg` signs raw `challenge_hidden`; anything else falls back to the Bitcoin message-signing path over `sha256(hidden) || sha256(visual)`. That would fail Aztec verification. Source: [sign_identity.py](https://github.com/trezor/trezor-firmware/blob/main/core/src/apps/misc/sign_identity.py), [requestLogin.ts](https://github.com/trezor/trezor-suite/blob/develop/packages/connect/src/api/requestLogin.ts), [messages-crypto.proto](https://github.com/trezor/trezor-firmware/blob/main/common/protob/messages-crypto.proto). For Phase A K1 on stock Connect, the origin needs to be effectively `gpg://...`, not `aztec://...`.

2. Headline from #4: yes, your pubkey handling is a real bug. Aztec expects `x || y` as 64 bytes, not a 65-byte uncompressed SEC1 point. `Ecdsa.computePublicKey()` returns `Buffer.concat([x, y])`, and `EcdsaKBaseAccountContract` slices bytes `0..32` and `32..64` directly. Sources: [ecdsa/index.ts](/Users/alejoamiras/Projects/aztec-packages/yarn-project/foundation/src/crypto/ecdsa/index.ts:18), [ecdsa_k/account_contract.ts](/Users/alejoamiras/Projects/aztec-packages/yarn-project/accounts/src/ecdsa/ecdsa_k/account_contract.ts:20). On the Trezor side, `SignedIdentity.public_key` is not 65-byte uncompressed anyway: `HDNode.public_key()` returns 33 bytes compressed. Sources: [modtrezorcrypto-bip32.h](https://github.com/trezor/trezor-firmware/blob/main/core/embed/upymod/modtrezorcrypto/modtrezorcrypto-bip32.h), [provider.ts](/Users/alejoamiras/Projects/aztec-hardware-wallet-poc/packages/adapter-trezor/src/provider.ts:62), [transport.ts](/Users/alejoamiras/Projects/aztec-hardware-wallet-poc/packages/adapter-trezor/src/transport.ts:14). So the real conversion is `compressed 33B -> x||y 64B`; your current `65B -> strip 0x04` model is not faithful.

3. `TrezorTransport.getPublicKey()` is not cleanly mappable to the real public APIs. There is no dedicated stock `GetPublicKey(identity, curve)` method for the SLIP-0013 auth key. `requestLogin`/`SignIdentity` returns the auth public key as a side effect; `GetECDHSessionKey` also returns a public key, but from the SLIP-0017 namespace `m/17'`, not the SLIP-0013 auth namespace `m/13'`, so it is the wrong key. Source: [get_ecdh_session_key.py](https://github.com/trezor/trezor-firmware/blob/main/core/src/apps/misc/get_ecdh_session_key.py). So for the auth key, you should cache the `public_key` returned by `SignIdentity`, then decompress it host-side.

4. On #1 specifically: current Connect exposes `requestLogin`, not a public raw `SignIdentity` method with `ecdsaCurveName`. The implementation calls `typedCall('SignIdentity', 'SignedIdentity', ...)`, but it only accepts `origin`, `challengeHidden`, and `challengeVisual`, and hardcodes `identity.index = 0`. `TrezorConnect.call({ method: 'requestLogin', ... })` is not an escape hatch; it routes through the same implementation. `TrezorConnect.call({ method: 'SignIdentity' })` is not a public callable method. Sources: [requestLogin.ts](https://github.com/trezor/trezor-suite/blob/develop/packages/connect/src/api/requestLogin.ts), [core-in-module.ts](https://github.com/trezor/trezor-suite/blob/develop/packages/connect/src/impl/core-in-module.ts), [callableMethods.ts](https://github.com/trezor/trezor-suite/blob/develop/packages/connect-common/src/callableMethods.ts). Lowest official escape hatch is `trezorlib.misc.sign_identity(..., ecdsa_curve_name=...)`; lowest JS-only escape hatch is your own `@trezor/transport` + `@trezor/protobuf` client.

5. On #2: your byte slicing in `unpackTrezorSecp256k1Signature` is structurally fine, but the marker-byte assumption is not. The underlying secp256k1/nist256p1 bindings return `header(1) || r(32) || s(32)` with `header = 27 + pby + 4*compressed`; there is no trailing `v`. But `SignIdentity` overwrites byte 0 with `0x00` for `gpg` and `ssh`, so on the actual Aztec raw-digest path you cannot recover `v` from the returned signature. Sources: [modtrezorcrypto-secp256k1.h](https://github.com/trezor/trezor-firmware/blob/main/core/embed/upymod/modtrezorcrypto/modtrezorcrypto-secp256k1.h), [modtrezorcrypto-nist256p1.h](https://github.com/trezor/trezor-firmware/blob/main/core/embed/upymod/modtrezorcrypto/modtrezorcrypto-nist256p1.h), [sign_identity.py](https://github.com/trezor/trezor-firmware/blob/main/core/src/apps/misc/sign_identity.py). So strip byte 0 and ignore it.

6. On #3: the wire format is protobuf `IdentityType`, not JSON. Firmware serializes it as `proto://user@host:portpath`, then derives the auth path from `sha256(pack("<I", index) || serialized_identity)`, taking the first 16 bytes into four hardened words under `m/13'`. Your comment that it is just `m/13' / sha256(identity)` is not exact. Source: [messages-crypto.proto](https://github.com/trezor/trezor-firmware/blob/main/common/protob/messages-crypto.proto), [sign_identity.py](https://github.com/trezor/trezor-firmware/blob/main/core/src/apps/misc/sign_identity.py). So `aztec://account/0` is representable, but only if you accept the wrong sigtype; for raw-digest signing, model `IdentityType` explicitly instead of a single string.

7. On #5: you can prove verifier compatibility in TS without PXE. Use `new Ecdsa('secp256k1').verifySignature(outerHash.toBuffer(), pubKey64, new EcdsaSignature(r, s, Buffer.from([0])))`. Do not pass `sha256(outer_hash)` into that API; barretenberg hashes the message internally with SHA-256, which matches Noir’s `sha256(outer_hash.to_be_bytes())`. `v` is ignored by the verifier. Sources: [bbapi_ecdsa.cpp](/Users/alejoamiras/Projects/aztec-packages/barretenberg/cpp/src/barretenberg/bbapi/bbapi_ecdsa.cpp:16), [ecdsa_impl.hpp](/Users/alejoamiras/Projects/aztec-packages/barretenberg/cpp/src/barretenberg/crypto/ecdsa/ecdsa_impl.hpp:128), [ecdsa_k_account_contract main.nr](/Users/alejoamiras/Projects/aztec-packages/noir-projects/noir-contracts/contracts/account/ecdsa_k_account_contract/src/main.nr:65).

8. On #6: fine. Offline address derivation is clean. Use `getContractInstanceFromInstantiationParams(...)` and read `instance.address`, or `CompleteAddress.fromSecretKeyAndInstance(secret, instance)` for the full tuple. Sources: [contract_instance.ts](/Users/alejoamiras/Projects/aztec-packages/yarn-project/stdlib/src/contract/contract_instance.ts:117), [complete_address.ts](/Users/alejoamiras/Projects/aztec-packages/yarn-project/stdlib/src/contract/complete_address.ts:66), [account_contract.ts](/Users/alejoamiras/Projects/aztec-packages/yarn-project/aztec.js/src/account/account_contract.ts:49). Hidden sub-landmine: salt is part of the address story.

**Next Step**
For the emulator -> real verifier proof, stop modeling this as `string identity + getPublicKey()`. For Phase A, use stock `trezorlib.misc.sign_identity` with explicit `IdentityType(proto='gpg', host='aztec', path='/account/0', index=0)` and `ecdsa_curve_name='secp256k1'`. Cache the returned 33-byte compressed `public_key`, decompress it to `x || y` 64 bytes, and add one unit test that feeds `(outerHash.toBuffer(), pubKey64, r, s)` into `new Ecdsa().verifySignature(...)`. Once that passes on emulator/device, you have the real Aztec-verifier proof and can redesign the TS transport around the actual upstream surface instead of the current fictional one.
