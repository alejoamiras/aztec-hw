Making the Aztec Ledger wallet tough enough for real money

A plain-language companion to plan.md. Milestone M11 — "Tier-0/Tier-1 hardening."

We already proved the wallet works: it signs Aztec transactions two different ways (ECDSA and Schnorr) and we ran the whole thing on a real test network. This milestone is about making it hard to attack — the difference between "cool demo" and "you'd trust it with funds."

Good news from our research: we compared our code to the closest shipped, audited wallet (Mina's Ledger app) and on the scary parts we're already at or above their bar. So this isn't a rewrite — it's a handful of targeted fixes, each one validated automatically before we move on.

The fixes, in plain words

P0 · measuring tools first

Build the test rigs before we touch anything

A "leak detector" that checks whether the chip's secret math takes a tell-tale different amount of time depending on the secret, plus a "size & speed budget" so we notice if a fix makes the app too big or too slow for the real device.

Why: you can't fix a leak you can't measure. We measure first so every later fix has a pass/fail gate.

P1 · the cheapest big win

Do the secret math twice and check it matches ("dual-derive")

When the device computes the secret number behind a signature, it now computes it twice, independently, and refuses to sign if the two don't agree. Plus a tidy-up pass that wipes secrets from memory on every exit and double-checks the chip's own crypto calls.

Why: attackers literally zap chips with voltage/laser glitches to corrupt one calculation and leak the key. Doing it twice and comparing catches that. This is the single highest-value fix and it doesn't change any output, so it's easy to prove safe.

P2 · write down the proof

Show the secret numbers aren't subtly biased

We derive secrets by hashing and taking a remainder. We prove (and add a test for) the fact that any bias is astronomically small — about 1 in 2²⁵⁸. No code change needed.

Why: a biased secret can leak a key over many signatures. We checked the math: ours is fine, and the "fix" people sometimes add (rejection sampling) would buy literally nothing here. Better to document it than cargo-cult it.

P3 · the delicate one

Make the secret math take the same path every time ("constant-time")

Remove three spots where the curve math takes a shortcut depending on the secret. We fix one shared core so it helps both the signature and the address hashing. The exact technique is chosen to fit the device's size/speed budget, and we keep the old version around until the new one is proven byte-for-byte identical.

Why: someone watching the chip's power use or timing can read out a key if the math "branches" on secret bits. Closing those branches is the classic hardware-wallet defense. This is the riskiest change, so it's gated three ways: identical output, the leak detector passes, and it still fits/runs fast enough.

P4 · tidy + stress-test

De-duplicate the account logic and throw garbage at the parser

Merge three copies of the same security-sensitive code into one. Then build a harness that feeds malformed/hostile messages to the device's actual message-handling code and watches for crashes or bad state.

Why: duplicated security code drifts apart and one copy gets a bug. And the message parser is the front door — a hostile computer will send it junk, so we attack it ourselves first.

P5 · the riskiest feature change

Support more kinds of accounts — safely

Today the device only fully supports one "shape" of account. We extend the wallet↔device message so it can carry the account's salt and recipe id. Crucially, the "who deployed it" stays pinned to a recipe the user reviewed — the computer is not allowed to just assert it.

Why: real users have varied accounts. But every new thing the computer gets to "tell" the device is a new way to lie to it. We let the computer specify only what's safe, and keep the sensitive part locked to something the user actually approved on-screen.

P6 · prove the rest works

Test all four ways of sending money — and check the private ones

We proved public→public on-chain; now we run the other three (public↔private combinations) end-to-end, and specifically double-check that the private ones still correctly tie the transfer to your account (not someone else's).

Why: the private modes are exactly where a "whose money is this?" check could quietly be missing. If it is, that's a real bug to fix, not just a test to tick.

P7 · second opinion

Final adversarial review

Send the whole diff to an independent AI reviewer (codex) with an explicit "try to break this" prompt, fix what's real, then tag the safe checkpoint.

Why: a fresh set of eyes catches what the implementer rationalized away.

How we make sure each step is actually safe

Every phase ends with the same automated gates, with no human needed to bless it: the math is checked byte-for-byte against trusted reference libraries, the app is rebuilt for the real device, and the full Schnorr flow (create account → fund → transfer) is run against the live test network by a headless browser. The two scariest phases (P3, P5) also get a focused codex review before we lock in a checkpoint tag. If a gate fails, we roll back to the last green tag.

Open questions (worth a human's gut-check)

Are exotic accounts actually coming soon? P5 (the risky message change) is only worth it if non-default accounts are imminent. If not, there's a cheaper "just refuse them clearly" option. You already chose the fuller approach — P5 is the natural place to change course if priorities shift.
Which constant-time technique? Two valid ways to do P3; the choice depends on the device's size/speed budget, which we only learn after P0. We'll pick then.
What if the private-transfer check is missing? P6 might uncover a genuine "sender not bound" gap in private modes. Fixing it could grow the milestone — do it here, or split it out?
